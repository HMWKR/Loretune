## 1. 목적과 범위

- 목적: 일반 대화 모델이 **저장된 편집(타임라인)이나 모션 변경안의 실제 프레임 몇 장**을 보고 답하게 한다. 지금은 모델이 텍스트로 된 상태만 받으며, 영상은 보지 못한다.
- 이 문서가 다루지 않는 것: 실제 구현, 실제 모델 호출, 외부 전송, 비용 승인. 이 항목들은 이번 범위 밖이다(PLAN-ko.md:126 "프레임·이미지 바이트 모델 전송 구현").
- 현재 상태 [검증됨]: 프레임 관찰 기능은 "없음 / 설계 문서만 S13 / 외부·유료 있음"이다(PLAN-ko.md:81). 이전 도구 감사도 "실제 프레임"을 일반 대화의 연결 공백으로 분류했다(`docs/design/CHAT-SESSION-PLAN.md:67`).

## 4. 이미지 블록 프로토콜과 상한

### 4-1. 현재 코드의 제약 [검증됨]
- 도구 결과는 **문자열 하나뿐**이다. `chat_protocols.py:49-51`은 결과를 `json.dumps`한 뒤 `dict(type='tool_result',tool_use_id=…,content=text)`로 만든다. 이미지 블록 경로는 없다.
- 결과 텍스트는 100,000자 이하다(`chat_protocols.py:50`). 모델 응답 쪽에서는 멀티모달 출력을 거절한다(`chat_protocols.py:32`).
- 이어쓰기는 **누적 이력**이다. `chat_models.py:99`는 `history+[assistant…, user(tool_result 블록들)]`로 이어 붙인다. 따라서 한 번 넣은 프레임은 이후 라운드마다 **다시 전송된다**.
- 전송 바이트 상한: `BoundedMessagesTransport(max_request_bytes=65536)`와 `BoundedCountTransport(max_request_bytes=65536)`(`chat_general.py:460-461`, `:623-624`). 이 값은 transport가 허용하는 최댓값이다(`anthropic_ontology.py:175-176`: `1 <= max_request_bytes <= 65536`, 넘으면 `ValueError`). 시스템 프롬프트, 도구 정의, 전체 이력, 이미지 base64가 모두 이 64KiB 안에 들어가야 한다. 이 상한을 올리려면 ontology 코드를 바꿔야 하므로 별도 결정 사항이다(§9 A3).
- **프레임은 두 본문에 들어가고 외부로 두 번 나간다** [검증됨: 코드 구조]. `count_body`는 `message_body`를 깊은 복사한 것이며 `max_tokens`만 뺀다(`chat_general.py:435`). 미리보기 항목은 두 본문을 모두 저장한다(`:443-444`). 승인 뒤 실행에서는 먼저 `count_body`로 토큰 수 확인을 보낸다(`:642-645` `transport.count`). 그다음에 `message_body`로 메시지를 보낸다. 따라서 프레임은 공급자에게 count_tokens 1회와 messages 1회, 모두 2회 전송된다.
- **브라우저에도 두 번 노출된다** [검증됨]. `public_preview`는 `message_body`와 `count_body`를 둘 다 클라이언트에 돌려준다(`chat_general.py:233-234`). 동의 카드는 "전달할 전체 내용 보기"에서 두 본문을 JSON 원문으로 그대로 출력한다(`general-chat-ui.js:55`). 즉 프레임 base64가 화면 텍스트로 두 번 표시된다.
- **이후 미리보기 행에도 복제된다** [검증됨: 코드 구조]. 이어쓰기 미리보기는 누적 이력(`continuation`)으로 새로 만들어진다(`chat_general.py:778`, `:789`). 그리고 본문 전체가 `general_chat_previews` 행에 직렬화된다(`:229-230`). 그래서 프레임은 남은 라운드의 미리보기 행마다 다시 저장된다(행마다 2벌).
- 예전 대화 경로(legacy)는 별도로 다뤄야 한다. 이 경로의 기본 도구는 `production_tools.TOOLS` 전체다(`chat_runtime.py:175`). 그리고 도구 결과를 이어쓰기 승인 없이 다음 메시지에 넣는다(`chat_runtime.py:331-332`, codex 검수 #7). 새 도구를 `TOOLS`에 추가하면 이 경로에도 노출된다.
- 입력 토큰 상한은 `MAX_INPUT = 4096`(`chat_general.py:28`)이다. 사전 count에서 `chat_general.py:646`, 사후 usage에서 `:744`가 이 상한을 집행한다. 라운드 수는 `MAX_ROUNDS = 4`(`:30`)다.

### 4-2. 제안 형식
- Anthropic: `tool_result.content`를 문자열 대신 블록 배열로 만든다. 순서는 `[{type:'text', text:<압축 영수증 JSON>}, {type:'image', source:{type:'base64', media_type:'image/png'|'image/jpeg', data:<b64>}} × N]`이다. 이미지 블록의 base64 형식은 Claude API 문서의 Vision 예시에서 확인했고, tool_result에 이미지를 담는 형식은 computer-use의 screenshot 결과에서 확인했다(claude-api 스킬 문서) [검증됨: 문서]. 다만 **Haiku 5.5가 이미지 입력을 지원하는지는 확인하지 못했다** [미확인]. 모델 레지스트리(`chat_models.py:8`)에는 입력 모달리티 항목이 없다. 확인 방법은 Models API의 `capabilities.image_input.supported`인데, 이것은 외부 호출이므로 승인이 필요하다.
- OpenAI·xAI: 현재 일반 대화 코드는 Claude 공급자만 받는다(`chat_general.py:181`: `result['provider'] != 'anthropic'`이면 거절) [검증됨]. 감사 문서의 원문은 "감사 당시 일반 대화 선택은 Claude만 허용"이다(`CHAT-SESSION-PLAN.md:67`). 이는 감사 시점의 진술이다. 이미지 지원이 확인되지 않은 공급자에는 **보내지 않고 거절**한다(AT38 "미지원 입력 … 전송 없음").
- **블록 배열은 이 도구의 결과에만 쓴다(음원 표식과의 결합)** [검증됨]. `check_music_context`는 음원 표식이 가리키는 tool_result의 `content`를 문자열로 보고 `json.loads`한다(`chat_general.py:312`). 이것이 `TypeError`나 `ValueError`로 실패하면 `'음원 조회 결과와 전송 내용의 연결을 확인하세요.'`로 바뀐다(`:314-315`). 이 검사는 미리보기를 만들 때(`:454-456`)와 전송 직전(`:618`)에 실행된다. 그리고 표식은 이후 라운드에도 이어진다(`:779`). 따라서 `result_message`(`chat_protocols.py:49-51`)를 모든 도구에 배열로 바꾸면, 특히 `search_project_context`에 바꾸면 음원 표식이 있는 이어쓰기는 **모두** 거절된다. 한 라운드에는 도구 호출이 1개뿐이다(`chat_general.py:751`). 표식은 `message_index`와 `tool_use_id`로 메시지 하나를 고른다(`:308-310`). 그래서 배열을 프레임 도구 결과에만 쓰면 음원 결과 메시지는 문자열로 남고 이 검사에 영향이 없다. 설계 결정은 다음과 같다. (a) 배열 형식은 프레임 도구 결과에만 쓰고 나머지 도구는 문자열을 유지한다. 또는 (b) 배열을 넓게 쓴다면 `check_music_context`를 비롯한 문자열 소비 코드가 두 형식을 모두 처리하도록 바꾼다. 어느 쪽이든 회귀 테스트를 필수로 둔다(§10).
- `normalize`(`chat_protocols.py:17-42`)는 그대로 둔다. 모델 **출력**의 멀티모달 블록은 계속 거절한다.
- 인계(`chat_protocols.py:55-70` handoff)는 메시지의 `text`만 옮긴다(`:57`). 그래서 프레임은 새 공급자 대화로 넘어가지 않는다. 이 동작을 불변 조건으로 테스트에 넣는다.

| 한 호출의 프레임 수 | **1~4**, 기본 1. **0장 요청은 거절**한다(렌더·전송 없음) | 작업 지시 상한 4. 이력이 누적되므로(`chat_models.py:99`) 한 턴 전체에서도 **누적 4장 이하**. `timeline_preview`는 한 번에 1프레임만 렌더하고 잠금을 기다리지 않는다(`app.py:423`). 따라서 4장은 잠금 호출 4회로 나눠 렌더하고, 4장 모두 같은 revision이어야 한다(호출마다 `:432`가 대조) |
| 바이트(**실제로 묶이는 상한**) | 승인값 ≤ N KiB(원본 바이트). 넘으면 거절하고 자동으로 품질을 낮추지 않음 | 64KiB 전송 상한(`chat_general.py:460-461`, `anthropic_ontology.py:175-176`)이 실제 한계다. count 본문과 message 본문에 각각 적용된다. 트랙 A1의 wave 1 오프라인 측정에 따르면 review·full_access의 첫 요청 `message_body`만으로 17,532바이트다(`tasks/A1-server-read-tools/token-budget.json`, 이력 없음) [추정: A1 재작업 중이라 값이 바뀔 수 있음]. 남는 몫은 약 48,000바이트다. base64는 원본의 4/3배로 늘어나므로, 첫 이어쓰기에서도 **원본 프레임 바이트는 모두 합쳐 약 36,000바이트 이하**다. 이어쓰기 이력이 쌓이면 남는 몫은 더 줄어든다. 640×360 PNG 한 장의 실제 크기는 측정하지 않았다 [미확인] |
| 토큰 | 프레임 포함 count가 `MAX_INPUT` 이하가 아니면 전송 거절(`chat_general.py:646` 재사용) | 공식 계산식: 이미지 1장 = ⌈너비/28⌉ × ⌈높이/28⌉ 시각 토큰(출처: platform.claude.com/docs/en/build-with-claude/vision, critic 판정의 인용) [미확인: 이 작업은 네트워크 금지라 원문을 다시 열지 않음]. 프로필별 계산: preview 640×360 → 23×13 = **299**, 4장 ≈ 1,196 / landscape 1920×1080 → 고해상도 등급이면 69×39 = 2,691, 표준 등급이면 축소 후(1456×816 가정) 52×30 = 1,560 / portrait 1080×1920도 등급에 따라 같은 값 [산수 검증됨, 등급별 축소 규칙과 Haiku 5.5의 등급은 미확인]. 1,568·4,784는 등급별 **이미지당 상한**이지 장당 비용이 아니다(1차 문서의 오류를 정정). preview 해상도에서는 토큰보다 64KiB 바이트 상한이 먼저 걸린다. 다만 텍스트 본문만으로도 4096을 넘는다는 추정이 이미 있다(PLAN §8-3 D20). 이 문제는 프레임과 별개로 먼저 풀어야 한다 |
| 저장 | run, journal에는 바이트를 넣지 않고 `sha256`, 크기, 해상도만 넣음 | 스펙 `:418`. 그러나 현재 구조에서는 바이트가 한곳에만 있지 않다(1차 문서의 "message_body에만 존재"를 정정). ① 미리보기 행의 `message_body`와 `count_body`에 2벌(`chat_general.py:435`, `:443-444`) ② 남은 라운드의 미리보기 행마다 다시 2벌(`:789`, `:229-230`) ③ 브라우저 응답과 동의 카드에 2벌(`:233-234`, `general-chat-ui.js:55`). 저장 위치와 보관 정책은 승인 항목이다(§9 A5) |

## 5. 전송 전 재검사와 동의 미리보기(data_scope) 변경

### 5-1. 현재 흐름 [검증됨]
1. 도구 실행 결과를 `result_message`로 만든다(`chat_general.py:777`). 그다음 `continuation`(`:778`) → `create_preview`(`:789`)로 **다음 전송 미리보기**를 만들고, 상태는 `awaiting_continuation_approval`(`:790`)가 된다. 사람이 이어쓰기를 승인하면 도구 결과가 Anthropic으로 **두 단계에 걸쳐** 나간다. 먼저 count_tokens에 `count_body`가 전송되고(`:642-645`), 그 결과가 `MAX_INPUT` 이하이면(`:646`) messages에 `message_body`가 전송된다. 두 본문 모두 도구 결과와 프레임을 담는다(§4-1).
2. 미리보기의 `data_scope`는 고정 문구다. `'입력한 대화 및 이 미리보기에 표시된 도구 결과만 포함; 자산 파일은 전송하지 않음'`(`chat_general.py:446`). 이 문구가 동의 카드의 "자료 범위"에 그대로 표시된다(`general-chat-ui.js:55`).
3. `data_scope`는 manifest 해시에 포함된다(`chat_general.py:242-245`). 그래서 문구가 바뀌면 manifest도 바뀐다.
4. 전송 직전에 다시 검사한다. 음원 문맥(`:618`), 이력(`:619`), binding과 만료(`:620`), manifest·본문 해시(`:621`), **실제 전송 바이트 sha256**(`:622-626`의 `message_wire_sha256`·`count_wire_sha256`).

### 5-2. 필요한 변경 (설계)
- **data_scope 문구가 사실과 어긋난다.** 프레임을 넣으면 "자산 파일은 전송하지 않음"(`:446`)이 거짓이 된다. 프레임이 포함된 미리보기에서는 문구를 바꾼다. 예: "입력한 대화, 도구 결과, **저장된 편집에서 렌더한 프레임 N장(해상도·크기·대상 컷/프레임 표시)** 포함. 원본 자산 파일 자체는 전송하지 않음". 동의 카드에는 프레임 썸네일과 개수를 함께 보여 준다. 사람이 **본 그대로** 전송되어야 한다(PLAN-ko.md:50 원칙 5). 문구에는 **전송 횟수**도 적는다. 예: "토큰 수 확인 요청과 메시지 요청에 각각 포함되어 공급자에게 2회 전송". 동의 카드의 고정 문장 "자료 파일 자체는 전달하지 않습니다"(`general-chat-ui.js:55`)도 프레임이 있을 때는 사실과 맞도록 바꾼다. 또 지금은 "전체 내용 보기"가 두 본문을 JSON 원문으로 출력한다(`:55`). 그래서 base64 텍스트를 그대로 보여 줄지, 썸네일과 해시로 바꿔 보여 줄지 정해야 한다.
- **전송 sha 재검사**: 프레임은 `message_body`와 `count_body` 안에 모두 들어간다. 그래서 기존 `message_sha256`·`count_sha256`·`message_wire_sha256`·`count_wire_sha256` 검사(`:621-626`)가 두 본문의 바이트 변조를 막는다 [추정: 구조상 자동 포함]. 그것과 별도로 결과에 `frames[].sha256`을 넣는다. 전송 직전에 **현재 편집을 같은 조건으로 다시 렌더해 해시를 대조할지**는 결정 항목으로 둔다. 다시 렌더하면 비용과 시간이 들고, 대조하지 않으면 렌더 후 편집이 바뀐 상황을 놓칠 수 있다. 이 문제는 음원의 `check_music_context`(`:290-318`)와 같은 구조다. 대안은 revision, 컷, 프레임, 렌더러 지문만 다시 대조하는 가벼운 방식이다.
- **권리 재검사는 긍정 확인 방식으로 한다.** 지금의 `check_rights`(`app.py:1020-1024`)는 `asset_rights.blocked=1`인 행만 막는다. 기록이 **없는** 자산(미확인)은 통과한다. 테이블에는 `blocked`, `reason`만 있고(`app.py:253`) 외부 전송 허용 여부를 담는 필드는 없다. 로컬 미리보기에는 이 정도로 충분하지만, 스펙 `:324`의 "외부 전송 허용 범위"를 만족하려면 **차단되지 않음 + 사용권 기록 있음 + 외부 전송 허용**을 모두 요구해야 한다. 이 필드와 판정 위치(자산 단위인지 작업 단위인지)는 데이터 모델 결정이므로 승인 항목이다. 음원 투영도 이미 `rights_status='unconfirmed'`를 따로 구분한다(`production_context.py:88`). 이 방식을 따른다.
- 권리 재검사 시점은 ① 도구 실행 시(`timeline_preview`의 `:438/:447`을 물려받음) ② 이어쓰기 승인 시 ③ 실제 전송 직전, 세 번이다. ②와 ③에서 하나라도 실패하면 전송을 거절하고 자동으로 다시 렌더하거나 재시도하지 않는다(PLAN-ko.md:51 원칙 6).

## 6. 결과 형식과 coverage 공개

모델에 돌려주는 텍스트 블록(압축 영수증)의 예:
```
{status:'observed', target:{kind:'timeline'|'motion', timeline_revision|proposal_id+scene_sha256, clip_index},
 frames:[{frame, seconds, width, height, media_type, bytes, sha256}],
 coverage:{sampled:N, of_frames:<컷 전체 프레임 수>, interval_frames, clips_observed:[i], clips_not_observed:'나머지 컷', audio:'관찰 안 함'},
 not_done:{full_video_analysis:false, audio_analysis:false, approval:false, applied:false, external_calls:0(도구 자체)},
 rights:{checked_at:[tool], status:'confirmed'|'blocked'|'unconfirmed'}}
```
- 위 coverage 형식은 스펙 `:134`와 원칙 9(PLAN-ko.md:54)를 따른다. 모델이 "영상 전체가 좋다"고 말하지 못하게, 시스템 문구에 "coverage 밖은 보지 않았다고 말할 것"을 추가한다. 현재 시스템 문구가 서버 상태만 설명하도록 정한 방식(`chat_protocols.py:70` instructions)과 같은 계열이다.
- 경로, grant, 내부 ID는 넣지 않는다. 작업 상태 조회의 비노출 원칙(`CHAT-SESSION-PLAN.md:45`)을 따른다.

## 7. 비용

- 대화 비용은 한 라운드 최악값을 사전 예약하는 방식이다. `worst = cost(spec, MAX_INPUT, MAX_OUTPUT)`(`chat_general.py:436`). Haiku 5.5 단가 `input_rate '.1'`, `output_rate '.5'`(USD/1M, `chat_models.py:8`)로 계산하면 (4096×0.1 + 4096×0.5)/1e6 = **USD 0.0024576/라운드**다(`chat_models.py:102-111` 공식) [검증됨: 산수]. 대화 전체 상한은 400,000 micro(USD 0.40) 이하다(`chat_general.py:433-434`).
- 프레임을 넣으면 생기는 영향:
  1. 입력 토큰 증가량은 §4-3 계산식으로 추정한다. preview 해상도에서는 장당 299, 4장이면 약 1,196이다. 입력 단가(USD 0.1/1M)를 곱하면 장당 약 USD 0.00003이다 [산수 검증됨, 계산식과 등급은 미확인]. 다만 텍스트만으로도 4096 초과가 이미 추정되어 있다(D20). `MAX_INPUT`을 올리면 라운드당 예약액(`chat_general.py:436`)도 비례해서 늘어난다.
  2. 이력이 누적되므로(`chat_models.py:99`) 프레임은 남은 라운드(최대 `MAX_ROUNDS=4`)마다 **다시 과금**된다.
  3. 라운드마다 프레임은 **count_tokens 요청과 messages 요청에 각각 담겨 2회 전송**된다(§4-1, `chat_general.py:645`). count_tokens 호출 자체의 과금 여부는 이번 작업에서 확인하지 않았다 [미확인]. 그러나 과금과 무관하게 **외부 전송 횟수**는 2배이므로 동의 문구와 승인 항목(A2)에 넣는다.
  4. 렌더 자체는 로컬 비용이다(FFmpeg, 공급자 호출 0).
  5. 실제 이미지 토큰 수는 공급자의 `count_tokens`로만 확정할 수 있다 [미확인]. 이것도 외부 호출이므로 승인 범위 안에서만 측정한다.
- 따라서 "프레임 관찰은 무료"라고 표시하지 않는다(스펙 `:362`).

## 8. 연관 위험: 음원 측정값 투영 (S11, 결정 D9로 보류)

D9 원문: "음원 측정값 투영(진행 중 이어쓰기 무효화 가능, 외부 전송 포함) | 보류 후 S13과 함께 설계"(PLAN-ko.md:142).

- **진행 중인 이어쓰기가 무효가 된다** [검증됨]. `check_music_context`(`chat_general.py:290-318`)는 전송 직전(`:618`)과 미리보기 생성 시(`:454-456`)에 `production_context.music_input`을 다시 계산하고(`:316`) 표식의 sha256과 대조한다(`:317`). 다르면 `MusicContextChanged`(`:318`)를 낸다. 표식의 sha는 조회 당시 결과로 고정된다(`:779-782`). 따라서 `music_input`(`production_context.py:74-104`)에 측정값 필드를 더하면 다음 두 가지가 일어난다.
  - 배포 전에 만들어진 대기 중 이어쓰기가 **모두** 해시 불일치로 거절된다.
  - 측정을 다시 하거나(분석 버전이 바뀌거나) 음원이 바뀌어 값이 달라지면 그때마다 진행 중인 턴이 거절된다.
  
  대안: 측정값을 `music_input`에 섞지 않고 별도 질의와 별도 표식으로 분리한다. 이 경우에도 표식 구조(`:299` 키 집합)가 바뀌므로 테스트를 의도적으로 수정해야 한다.
- **프레임 도구의 결과 형식도 같은 무효화 경로에 걸린다** [검증됨]. `check_music_context`는 tool_result의 `content`가 문자열이라고 보고 `json.loads`한다(`chat_general.py:312`). 블록 배열이 음원 표식 메시지에 들어가면 `:314-315`에서 진행 중인 이어쓰기가 거절된다. 배열 형식의 적용 범위는 §4-2의 결정 (a)와 (b)를 따르고, 회귀 테스트는 §10에 둔다.
- **자산에서 파생된 특징이 외부로 전송된다.** `music.waveform`(`music.py:16-17`, "Bounded actual PCM envelope")처럼 실제 음원에서 계산한 값은 파일이 아니어도 **미공개 곡의 파생 정보**다. 지금의 data_scope 문구 "자산 파일은 전송하지 않음"(`chat_general.py:446`)은 이 경우를 설명하지 못한다. 스펙 `:324`의 "미공개 곡의 외부 전송 허용 범위"를 작업마다 확인해야 한다. rights가 `unconfirmed`(`production_context.py:88`)인 음원의 측정값은 보내지 않는 것을 기본으로 둔다.
- 결론: 프레임과 측정값은 같은 "자산 파생 데이터의 외부 전송" 문제다. 그러므로 data_scope 문구 체계, 긍정 권리 확인, 해시 표식 분리를 **한 번에** 설계하고 승인받는다.

| A1 | 모델 | 이미지 입력을 보낼 정확한 모델 ID(예: `claude-haiku-5-5`)와, 그 모델의 이미지 지원 확인 방법(Models API 조회 = 외부 호출) |
| A2 | 자료 | 어떤 작품, 편집, 모션의 프레임을 보낼지. 실제 얼굴, 미공개 곡, 공개 전 설정의 포함 여부. 외부 전송 허용 필드를 신설할지와 그 판정 단위(§5-2). **전송 지점이 두 곳**이라는 점(라운드마다 count_tokens와 messages, §4-1)과 브라우저 응답과 동의 카드에 두 본문이 노출된다는 점(`chat_general.py:233-234`, `general-chat-ui.js:55`)을 포함한다 |
| A3 | 개수와 크기 | 호출당, 턴당 프레임 수(0 거절, ≤4). 프레임당 바이트 상한, 해상도. **실제로 묶이는 상한은 64KiB 전송 바이트**다(§4-3). 선택지는 다음과 같다. ① 축소 또는 JPEG 변환(새 축소 단계 추가) ② transport 바이트 상한 상향(`anthropic_ontology.py:175-176`의 65536 상한을 바꾸는 ontology 변경) ③ Files API(`file_id` 참조)로 요청 본문을 작게 유지. ③은 이력이 다시 전송될 때 본문 크기를 줄이지만, **공급자 저장소에 별도로 업로드하는 외부 전송**이다. 따라서 업로드·보관·삭제를 따로 승인받아야 한다. 이 밖에 `MAX_INPUT` 상향 여부(D20과 함께) |
| A4 | 최대 비용 | 라운드당 예약액 변화와 대화 총상한(현재 ≤ USD 0.40). 이미지 토큰을 측정하는 `count_tokens` 호출 예산 |
| A5 | 보관 | base64가 남는 모든 위치의 보관 기간과 삭제 정책: 미리보기 행의 `message_body`·`count_body` 2벌, 남은 라운드의 미리보기 행마다 다시 2벌, 브라우저 응답(§4-3 저장 행). 계정 삭제는 영구 금지이고, 다른 삭제는 대상별로 개별 허용을 받는다 |
| A6 | 재검사 수준 | 전송 직전에 다시 렌더해 해시를 대조할지, 메타데이터만 대조할지(§5-2) |
| A7 | 음원 측정값(S11) | 표식을 분리하는 방식과, 진행 중 이어쓰기가 무효가 되는 것을 받아들일지(§8) |

이 승인들은 1차 녹화 검토나 AI 영상 호출 승인과 **별개다**(`CHAT-SESSION-PLAN.md:29`). Full Access 같은 자율 등급으로도 대신할 수 없다. 외부 전송, 비용, 권리는 항상 사람이 정한다(PLAN-ko.md:55 원칙 10). Full Access가 자동으로 초안을 만들 수 있는 명령은 5개의 타임라인 명령뿐이며 이 도구는 여기에 들어가지 않는다(`CHAT-SESSION-PLAN.md:39`).

## 10. 구현 시 접점과 테스트 (승인 후)

- 접점은 PLAN-ko.md:61 체크리스트를 따른다. TOOLS(`production_tools.py:10~`) → `chat_protocols` 스키마와 **블록 배열 결과** → validate → ALLOWED_TOOLS(`chat_general.py:34`) → execute 분기 → compact_result → UI 동의 카드(`general-chat-ui.js:55`)에 프레임 표시.
- 필수 테스트:
  - 미지원 공급자나 모델에는 이미지 0개를 전송하고 거절한다(AT38).
  - 5장 이상, 바이트 초과, `MAX_INPUT` 초과는 거절한다.
  - 권리가 blocked이거나 unconfirmed이면 전송을 거절한다.
  - 렌더 후 편집 revision이 바뀌면 거절한다.
  - data_scope 문구가 프레임 수와 일치한다.
  - 이어지는 라운드에 프레임이 다시 포함되는 것을 비용 예약에 반영한다.
  - 인계 시 프레임 0개.
  - run과 journal에 base64 0바이트.
  - **프레임 0장 요청**은 렌더 호출 0회, 미리보기 생성 0회로 구조화 거절한다.
  - **다른 대화의 편집이나 컷**은 거절한다. 대화 범위는 모델 인자에서 받지 않는다. 서버가 turn의 `conversation_id`를 `timeline_preview(..., conversation)`에 넣고, `chat_sessions.scoped`(`app.py:427`)가 범위를 정한다. 다른 대화의 컷 번호나 revision을 지정하면 렌더 0회로 거절해야 한다. 이때 그 대화의 존재나 내용이 결과에 드러나지 않아야 한다.
  - **잠금 충돌**: `timeline_preview_lock`은 기다리지 않고 바로 `Conflict`를 낸다(`app.py:423`). 도구는 이것을 구조화 거절(예: `status:'busy'`)로 돌려준다. 이 거절 때문에 turn이 `outcome_unknown`이 되거나 자동 재시도가 일어나지 않는지 확인한다. 4장 요청 중에 충돌이나 revision 변경(`:432`, `:444`)이 생기면 일부 프레임만 보내지 않고 전체를 거절한다.
  - **음원 표식 결합 회귀**: `search_project_context` 음원 결과(표식 생성 `chat_general.py:779-782`) 다음 라운드에 프레임 도구의 블록 배열 결과가 이어지는 경우를 만든다. 그 상태에서 미리보기 생성(`:454-456`)과 전송 직전 검사(`:618`)의 `check_music_context`가 통과하는지 확인한다. 그리고 `search_project_context` 결과의 `content`가 문자열로 남는지 단언한다(§4-2 결정 (a)). 결정 (b)를 택하면 배열 형식의 음원 결과도 통과하는지 함께 확인한다.
  - 프레임은 `count_body`와 `message_body`에 모두 들어 있고 해시 검사(`:621-626`)가 두 본문 모두에 적용되는지 확인한다. 동의 문구에 전송 2회가 표시되는지 확인한다.
  - 프레임 도구가 예전 대화 경로(`chat_runtime.py:175` 기본 `TOOLS`)에 노출되지 않는지 확인한다.

## 11. 미확인·가정

- [미확인] Haiku 5.5가 이미지 입력을 지원하는지, 그리고 어느 해상도 등급인지(표준/고해상도). 토큰 계산식(⌈w/28⌉×⌈h/28⌉)은 critic이 인용한 공식 문서에서 가져왔다. 이 작업에서는 네트워크 금지로 원문을 다시 열지 않았다. count_tokens 호출의 과금 여부도 확인하지 않았다. 640×360 프레임 PNG의 실제 바이트도 측정하지 않았다.
- [추정] 64KiB에서 남는 여유가 약 48,000바이트라는 값. A1 wave 1 측정(첫 요청, 이력 없음)을 기준으로 했으며, A1 재작업과 이어쓰기 이력에 따라 줄어든다.
- [추정] 프레임이 두 본문에 포함되면 기존 `message_wire_sha256`·`count_wire_sha256` 검사가 바이트 변조를 막는다(`chat_general.py:622-626` 구조 기준. 실제 테스트는 아직 없음).
- 가정: 이 문서는 설계 제안일 뿐이다. 이 문서가 있다는 것만으로 승인되었거나 구현되었다고 보지 않는다.
