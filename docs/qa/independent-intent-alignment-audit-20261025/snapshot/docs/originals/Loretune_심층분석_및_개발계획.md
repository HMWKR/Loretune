# Loretune 심층 분석과 첫 개발 계획

기준일: 2026-10-24. 원본 대화·첨부 자료를 내려받아 읽고 정적으로 확인한 분석이다. 원본에서 제공한 Python 프로그램은 이번 분석에서 실행하지 않았다. 고객 컴퓨터, 실제 Loretune 프로젝트, 외부 유료 모델, 결제, 배포는 변경하지 않았다.

## 1. 결론

Loretune은 일반적인 ‘음원을 넣으면 영상을 생성하는 앱’보다 **같은 음악 IP의 두 번째·세 번째 작품에서 승인된 설정과 수정 이유를 재사용하는 제작 공간**으로 좁혀야 한다. 첫 구현의 합격선은 화면 수가 아니라 ‘이번 작품만의 수정은 다음 작품에 잘못 전파되지 않고, 승인된 기억은 새 곡에 적용되며, 한 샷을 바꿔도 나머지는 유지되는가’다.

자료는 상당히 상세한 **기획·설계 패키지**다. 제품 프런트엔드, 서버, 공급자 어댑터, 실제 DB migration, 배포 구성은 없다. 동작 코드가 있는 것은 문서 지식 CLI와 오프라인 비용 계산기뿐이다. 따라서 파일을 옮기는 일과 플랫폼을 구현하는 일을 분리해 진행해야 한다.

지금 유일하게 미확정인 실행 입력은 **사용자가 말한 Loretune의 실제 작업 위치와 환경**이다. 공유 대화에는 저장소, 로컬 경로, 서비스 URL이 없다. 이름은 대화 후반의 브랜드 제안이다. 원본에서 ‘아로결’도 제안됐지만, 사용자가 선택한 이름으로 확인되지 않았으며 현재 요청의 Loretune을 바꾸면 안 된다.

### 실제로 발견한 패키징 결함

전체 ZIP 안의 project_kit에는 registry가 참조하는 구버전 파일의 해시 목록(MANIFEST.sha256.json)이 빠져 있다. 별도 CLI ZIP에는 그 파일이 있으며 SHA256은 registry 기대값 해당 파일의 기대 해시와 일치한다. 별도 CLI에는 .gitignore도 있다. 두 키트에서 공통 파일은 전부 바이트가 같다.

따라서 **별도 CLI ZIP을 작업용 키트 기준으로 쓰고 전체 ZIP은 문서 원본으로 보관**하는 것이 가장 단순하다. 별도 CLI의 등록 Document 파일 77개는 모두 존재하고 저장된 해시와 일치하는 것을 이번에 독립 정적 확인했다. 전체 ZIP만 이용할 경우 작업 사본에 누락 파일을 정확히 복원한 뒤 검증해야 한다. 원본 ZIP, 동결 자료, 과거 기록을 고쳐서 검증을 통과한 것처럼 만들지 않는다. 제공된 ‘오류 0’ 테스트 보고서는 패키징 이전의 결과이며, 현재 전체 ZIP이 그대로 오류 0이라는 증거가 아니다.

## 5. 제품의 핵심 데이터 계약

반드시 분리할 네 종류:
1. 공식 설정: 출처·승인자·IP·분기·활동기·효력 시점이 있는 사실.
2. 제작 자산: 파일 버전·원본과 파생 관계·사용 권리·철회 상태가 있는 이미지·영상·음원.
3. 취향: 이유·적용 범위·예외·중지 상태가 있는 연출 규칙. 예산 때문에 고른 후보는 미적 선호가 아니다.
4. 피드백 사건: 어느 버전·어느 시간·어느 샷에 대한 원문인지 보존. 공식 설정이나 영구 취향으로 자동 승격하지 않는다.

기억의 기본 범위는 좁게 둔다. 샷 → 프로젝트 → 활동기 → IP 전체를 명시적으로 구분한다. 꿈 장면이나 가사 은유는 세계관 사실이 아니다. 작품 채택, 공식 설정 승인, 장기 취향 승인은 다른 동작이다.

문맥 검색은 임베딩 유사도보다 먼저 조직·IP·사용자 권한·권리·공개 가능 범위·시점·분기·승인 상태를 필터링해야 한다. 실제 선택된 근거와 버전을 스냅샷으로 저장한 다음 장면 계획과 실행에 연결해야 하며, 생성 후 그럴듯한 설명을 붙이는 방식으로 대체하면 안 된다.

제품의 고객 IP 온톨로지와 개발팀의 문서 온톨로지는 별개다. 문서 CLI의 registry를 고객 runtime DB로 그대로 쓰지 않는다.

## 6. 우선순위와 첫 수직 구현

아래 우선순위는 이번 분석의 실행 제안이며 사용자나 원본 작성자가 이미 채택한 결정으로 표시하지 않는다. 원본 카탈로그는 release_gate와 baseline_gate를 두지만 G0로 태그된 요구가 없고 96개 중 75개가 G1 기준선에 걸려 있다. 문서의 G0 서술을 실제 개발 범위와 시험에 연결하는 작은 계약 묶음부터 별도로 확정해야 한다.

### G0-A: 비용 없는 기준 수립과 실패 시험

- 대상 저장소·기존 파일·AGENTS·기술 스택을 읽고 원본을 불변 자료로 가져온다. 기존 프로젝트를 덮어쓰거나 새 scaffold로 교체하지 않는다.
- 원본 v2, 과거 v1, 이번 분석, 구현 결정과 작업 로그의 디렉터리를 분리한다. 별도 CLI 키트를 기준으로 가져온다.
- 조직/IP/프로젝트/곡/샷/자산/설정 후보/승인 설정/피드백/취향 범위/실행 스냅샷의 최소 모델과 명시적 버전을 만든다.
- 권리 확인된 테스트 자료 또는 명백한 fixture만 사용한다. fixture 화면을 실제 고객이나 성공 사례처럼 보이지 않게 표시한다.
- 실제 모델과 결제 대신 mock provider를 두고 중복 클릭, 콜백 중복·역전, 접수 불명, 취소, 버전 불일치, 예산 경합을 시험한다.

### G0-B: 15~30초 end-to-end 기술 경로

자료 등록 → 설정 후보 → 승인 → 새 곡/브리프 → 구간과 샷 계획 → 근거·예산·기준 프레임 승인 → 한 샷 실행 → 검토·선택 → 렌더/내보내기 → 기억 후보 범위 승인 → 새 곡의 후속 프로젝트.

핵심 요구 연결:
- 정체성과 권리: FR-001~003, FR-007~009, FR-013, FR-016, FR-018.
- 승인 기억: FR-019~024, FR-025~028, FR-036.
- 곡·계획: FR-031~033, FR-037, FR-039~042.
- 비용·실행·복구: FR-043~046, FR-049~053, FR-080~083.
- 비교·부분 수정·출력: FR-055~056, FR-059~063, FR-067~069.
- 다음 작품과 측정: FR-012, FR-072~076.

최초 UI는 IP 기준함, 작품 시작/브리프, 샷 보드+미리보기+근거 패널, 검토/부분 수정, 실행·비용 상태 정도로 연결한다. 38개 화면을 모두 먼저 만드는 것은 검증을 늦춘다. 타임라인은 처음부터 범용 편집기와 경쟁하지 말고 음원·샷·기본 자막·선택 테이크를 조립하는 수준부터 시작한다.

첫 합격 사례:
1. 프로젝트 A의 ‘이 샷만 따뜻하게’가 프로젝트 B 전체 취향이 되지 않는다.
2. 승인한 지속 취향과 새 활동기의 의상만 프로젝트 B에 정확히 적용한다.
3. 새 곡은 새 박자·가사 시간축을 가진다. 기존 음원의 타임코드를 복사하지 않는다.
4. 12개 샷 중 3번 샷만 바꾸면 다른 11개의 take ID·승인·음원·자막은 그대로다. 길이가 달라지면 명시적 타이밍 재검토가 필요하다.
5. 접수 불명 상태에서 새 유료 생성 요청을 보내지 않으며, 비용 미확정 상태를 성공/무료/환불로 단정하지 않는다.
6. 권리가 철회된 자산은 과거 결과의 보존 여부와 별개로 새 공급자 요청에 다시 전송되지 않는다.

공급자 실제 호출 단계는 입력 권리·전송 범위·제공 조건·API 연결·지출 한도를 확인한 뒤 진행한다. 파일 다운로드 승인이 유료 모델 호출이나 외부 공개·신규 자격증명 생성을 자동 승인하지는 않는다.

### G1: 제한된 유료 검증

지원 범위를 30~60초의 리릭/승인 자산 편집/단일 인물 짧은 생성/혼합형으로 제한한다. 정확한 다인 군무, 긴 립싱크, 보장된 얼굴 일관성은 초기 약속에서 제외한다. 3팀 각 3개 서로 다른 요청, 최소 2곡으로 기억 효과를 검증한다. 180초는 현재 원가 모델링 시나리오이지 검증된 제품 지원이 아니다.

### G2/G3: 증거가 있을 때 확장

다중 IP·활동기·외부 협업·반복 결제와 지원 원가를 확인한 뒤 템플릿·배치·외부 편집기 교환·기업 인증·고급 퍼포먼스를 늘린다. 권한 회수, 사용 중지, 데이터 이관·삭제, 백업 복원, 결제 취소·원장 대사는 ‘고급 화면’이 아니며 제한 상용 운영 전에 필요하다.

## 9. 추가 정적 감사에서 확인한 기술 계약의 공백

아래는 문서·JSON·SQL을 읽어 찾은 구현 전 보완점이다. 실행 중인 서비스의 장애나 실제 악용을 확인한 결과는 아니다.

| 계약 공백 | 개발 시 생기는 문제 | 먼저 정할 일 |
|---|---|---|
| 타임라인 EditDecision은 takeId를 필수로 요구하지만, 승인된 기존 이미지·영상의 자산 합성에서 자산을 take로 연결하는 계약이 불명확하다 | 기존 자산 중심 모드를 일관되게 저장·렌더하기 어렵다 | 자산 소스와 생성 테이크를 명시적으로 구별하거나 asset-to-take 변환을 정의한다 |
| ExportCreate는 estimate를 요구하지만 EstimateCreate는 생성 샷·모델·후보 수 중심이다 | 새 생성 없는 렌더·내보내기 비용 승인이 모호하다 | generation과 render/export 견적 유형·단위·예약 상태를 분리한다 |
| If-Match 사용은 ETag를 전제로 하지만 143개 operation의 응답에 ETag 헤더 계약이 없다 | 클라이언트가 어떤 버전을 기준으로 안전하게 편집할지 불명확하다 | 읽기 응답의 ETag 또는 명시적 resource version을 mutation 계약과 함께 정한다 |
| AssertionRevision 응답은 추가 필드를 허용하지 않으면서 생성 입력의 시점·활동기·범위 정보를 생략한다 | 승인된 사실이 어떤 시점·범위에 유효한지 round-trip 보존이 어렵다 | 읽기·쓰기·revision 모델에서 적용 범위와 시간 축을 일치시킨다 |
| 요구 카탈로그에 G0 태그가 없고 75/96개 요구가 G1 기준선에 연결돼 있다 | 첫 기술 검증의 완료 기준이 지나치게 크거나 모호해진다 | 소수 화면·엔드포인트·데이터·반례 시험으로 G0 계약을 잘라서 정의한다 |

따라서 기존 OpenAPI/SQL 전체를 그대로 코드 생성해 완성품처럼 연결하는 것보다, 첫 수직 경로의 계약을 명확히 하고 UI·API·DB·워커·검증을 함께 맞추는 편이 안전하다.

## 10. Loretune으로 가져올 순서

1. 실제 Loretune 작업 위치와 기존 프로젝트 구조를 확인한다. 기존 작업을 덮어쓰지 않는다.
2. 통합 문서 ZIP과 원문은 출처 자료로 보관하고, 별도 CLI ZIP을 작업용 지식 키트의 기준으로 사용한다.
3. 현재 v2·과거 v1·새 분석·구현 결정을 분리한다. 원본 기준 자료는 수정하지 않고 변경 사항을 새 문서·버전으로 남긴다.
4. 실제 실행 가능한 범위를 검토한 뒤 문서 CLI와 계산기의 시험을 새 환경에서 다시 확인한다. 과거 테스트 보고서를 새 실행 결과로 사용하지 않는다.
5. 위 기술 계약 공백을 해결하고, mock 공급자로 G0의 정상·실패 경로를 구현한다.
6. 모델 호출 권한·자료 사용 범위·예산을 정한 뒤 실제 한 샷 생성으로 전환한다. 그 다음 15~30초 기술 경로, 제한된 30~60초 파일럿 순으로 진행한다.
7. 작업 보고는 문서·코드 변경, 실제 통과한 시험, 아직 구현하지 않은 부분, 실제 생성 품질·비용을 분리한다.

## 1. 직접 확인한 것과 확인하지 않은 것

- 175개 파일을 정적으로 목록화했다. OpenAPI JSON, SQL 전체, 핵심 기술/제품/검증 문서, 요구 카탈로그, fixture 등록부, Python 코드와 제공된 시험 보고서를 읽었다.
- 직접 센 결과: 116개 경로, 143개 operation, 122개 schema. 33개 `core`, 110개 `planned`이며 **143개 모두 `not_implemented`**다.
- JSON 내부 `$ref` 1,672회 참조가 모두 해석된다. 이것은 자체 참조 확인이며 공인 OpenAPI 검증기 실행이나 API 서버 시험이 아니다.
- SQL은 51개 테이블, tenant 열을 둔 48개 테이블, tenants 자체를 포함한 FORCE RLS 선언 49개다. SQL을 파싱하거나 PostgreSQL에 적용하지 않았다.
- 요구 96개 모두 `runtime_verified=false`다. 정확한 단계 필드 `release_gate`는 G1 65개/G2 25개/G3 6개이며, 최소 안전 조건을 반영한 `baseline_gate`는 G1 75개/G2 15개/G3 6개다. **75개라는 수는 `priority`가 아니라 `baseline_gate == "G1"` 필터 결과다. G0 전용 요구 목록은 없다.**
- 12개 제품 fixture 모두 `planned`, 실제 파일/해시/검수자 없음, `ready_for_execution=false`다. 제품 수용·통합 시험 JSON은 테스트 코드나 실행 결과가 아니다.
- 제공된 로컬 시험 보고서가 명시한 `kb.py`, CLI 시험, 비용 계산기/config/시험의 SHA-256은 현재 파일과 일치한다. 보고서에 적힌 26개 통과는 전달본의 주장과 바이트가 맞는다는 뜻이며, 이번 감사에서 재실행한 결과가 아니다.
- 다운로드한 Python 실행, 의존성 설치, 유료 API 호출, 실제 DB/서버 변경, 사용자 컴퓨터 접근은 하지 않았다. 패키지 원본은 수정하지 않았다.

계수와 해시는 원본 파일을 직접 읽어 별도 확인했다.

입수 무결성 추가 사항: 파일 입수 확인에서 전체 ZIP 안의 kit는 레지스트리가 참조하는 `archive/v1/output/MANIFEST.sha256.json` 1개가 빠진 반면, 독립 CLI ZIP에는 기대 해시와 일치하는 파일 및 `.gitignore`가 있으며 공통 파일이 동일함을 확인했다. 독립 CLI kit의 등록 Document 77개도 존재·해시 일치함을 확인했다. 따라서 CLI 사용 기준선은 독립 CLI ZIP을 권한다. 이는 파일 확인 결과이며 실행 시험은 아니다. 원본 ZIP을 조용히 보정하거나 검증된 것으로 덮어쓰지 않는다.

## 2. 실제 코드의 범위

## 3. 유지할 설계 강점

1. 사실·자산·선호·피드백, 실존자·허구 인물, 제작 승인·정사 승인·배포 승인을 분리한다.
2. 불변 버전과 스냅샷, 출처, 의존 샷 추적으로 과거 작품 보존과 부분 수정의 기반을 둔다.
3. 생성 상태와 과금 확정 상태를 분리하고, 제출 불명 상태에서 무작정 다시 POST하지 않도록 한다.
4. 원장 예약·job·outbox를 한 트랜잭션으로 다루고 중복 웹훅·역순 사건·늦은 결제를 명시한다.
5. 권한·권리 재확인, 검역 업로드, SSRF, 문서 프롬프트 주입, 삭제 전파와 복원 후 tombstone 재적용을 초기 안전 요구로 포함한다.
6. 문서 검증, 로컬 도구 시험, 제품 구현, 모델 품질, 실제 유료 수요를 구별한다. 이 정직한 상태 표시는 Loretune에서도 유지해야 한다.

## 4. 구현 전에 좁혀야 할 계약 결함·공백

아래는 **설계 문서의 공백**이다. 실행 서버가 없으므로 이미 악용 가능한 운영 취약점으로 단정하지 않는다.

### A. 자산 합성 경로가 타임라인 계약에서 닫히지 않는다 — G0 차단

`EditDecision`은 모든 컷에 `takeId`를 필수로 요구한다. SQL `takes`는 `job_id`, `generation_manifest`, `technical_validation`을 요구하지만, 승인된 정지 이미지나 기존 클립을 take로 편입하는 명령/출처 모델은 명확하지 않다. 제품은 자산 합성·혼합형을 첫 경로로 제안하므로 이 부분을 먼저 결정해야 한다.

해결: `source: {kind: asset_revision|take, ...}` 판별 union을 정의하거나, 비생성 자산을 제작 take로 등록하는 명시적 명령과 `origin=uploaded|generated|composed`를 둔다. 비생성 자산을 외부 생성 성공으로 집계하지 않는다. 정지 이미지 duration, crop/scale, 원본 timebase, 음원 mute 규칙까지 좁은 스키마로 고정한다.

근거: OpenAPI `EditDecision`(YAML 14398행), `ProjectVersionCreate`; SQL `takes`(540행). 관련 FR-047/055/056.

### B. 렌더 견적을 만드는 계약이 없다 — G0 차단

`ExportCreate`는 `estimateId`와 `budgetLimit`를 필수로 받는다. 그러나 유일한 `EstimateCreate`는 `shotRevisionIds`, `modelReleaseId`, `maxAttemptsPerShot`를 필수로 요구하는 생성 견적이며, `projectVersionId`나 내보내기 프로필을 지정하는 render-only 견적은 없다. `outputProfile`은 자유 객체여서 의미를 추측할 수는 있어도 견적과 실행 대상의 정확한 일치를 보장할 계약은 아니다.

해결: generation/render/export용 estimate 종류를 분리하거나 명시적 판별 union을 둔다. 견적 해시에 대상 프로젝트 버전·출력 프로필·입력 해시·가격 버전·상한을 포함하고, 실행 시 같은 요청인지 검증한다. 무료 포함 렌더도 tenant quota를 갖되 가짜 생성 모델을 요구하지 않게 한다.

근거: OpenAPI `EstimateCreate`(14141행), `ExportCreate`(14562행).

### C. 버전 충돌 계약의 입출력이 불완전하다 — G0 차단

공통 `IfMatch`는 “마지막 조회가 반환한 ETag”를 요구하지만 전체 응답에 ETag 헤더 선언이 0개다. 여러 PATCH는 `If-Match`가 유일한 기대 버전 입력이다. `patchSongSegments`는 헤더 외에도 `expectedAnalysisRevision`을 요구하지만 두 값이 불일치할 때 무엇을 기준으로 하는지 명확하지 않다.

또한 `TakeSelectionCreate`는 `expectedShotRevision`만 확인한다. 같은 shot revision의 서로 다른 take를 동시에 선택할 때의 selection revision/현재 선택 포인터와 충돌 규칙은 없다. `ApprovalCreate.expectedRevision`도 불변 대상 버전과 승인 상태의 동시성 버전을 구별해야 한다.

해결: GET/수정 응답 ETag 계약, 비교 규칙, 원자적 compare-and-swap, 선택/승인 상태의 버전과 전이를 명세한다. 두 사용자가 같은 revision을 읽고 서로 다른 선택/승인/철회를 제출하는 시험을 추가한다.

근거: OpenAPI `IfMatch`(12923행), `TakeSelectionCreate`, `ApprovalCreate`(13491행); SQL `approval_decisions`(633행).

### D. 정사 revision 응답이 시간·범위를 잃는다 — 초기 계약 보완

`AssertionCreate`/`AssertionRevisionCreate`는 era, story 날짜/순서 범위를 받는다. SQL도 저장한다. 하지만 상세 `AssertionRevision` 응답에는 `eraId`, `validStoryFrom/To`, `storyOrdinalFrom/To`, `scope`가 없고 `additionalProperties=false`라 서버가 이를 반환하면 현 응답 스키마에 어긋난다. 설정의 시점·분기가 제품 핵심이므로 응답·검토 UI가 누락된 필드를 추측해서는 안 된다.

해결: 생성/조회/수정 응답을 공통 정사 revision 스키마로 정렬하고 모든 유효 범위와 승인 상태를 왕복 시험한다. scope 변경을 허용할지, 초기 scope를 반드시 계승할지도 명시한다.

근거: OpenAPI `AssertionRevision`(15876행); SQL `assertion_revisions`(168행).

### E. “버전 있는 도메인 JSON”이 실제로는 대부분 열린 객체다 — G0 차단

권리 선언, shot spec, snapshot manifest, output profile, transform, layers, 모델 limits, 선호 rule 등은 `additionalProperties=true` 객체다. 설명에는 별도 버전 스키마 검증을 요구하지만 해당 G0 도메인 스키마와 공통 버전 필드가 충분히 제공되지 않는다. 이 상태에서 모델 출력을 곧바로 DB/공급자/FFmpeg에 넘겨서는 안 된다.

해결: G0에서 지원하는 정확한 JSON Schema와 typed DTO를 추가한다. 임의 공급자 옵션·파일 경로·shell/FFmpeg 표현식을 허용하지 않고, manifest canonicalization/hash 입력과 이전 버전 변환 규칙을 고정한다.

근거: OpenAPI `UploadCreate`, `ShotRevisionCreate`, `ContextSnapshot`, `EstimateCreate`, `EditDecision`; 기술서 4.4의 애플리케이션 제약.

### F. durable mutation 멱등성 저장소가 불충분하다 — 외부 제출 전 차단

많은 생성/등록/승인 API가 Idempotency-Key를 요구한다. SQL에는 job과 approval의 키 유일성이 있으나 다른 동기 mutation의 요청 해시·진행 상태·재생 응답을 지속하는 공통 저장 계약이 없다. approval 행 자체에도 요청 해시가 없다. 키 UNIQUE만으로 “같은 키+다른 요청 409, 같은 요청은 같은 결과”를 구현했다고 볼 수 없다.

해결: `(tenant, operation, key)` 멱등성 레코드에 대상 경로/ID를 포함한 정규 요청 해시, 결과/상태, 보존 기한을 저장한다. mutation과 같은 트랜잭션에서 확정한다. 재생 전에 현재 권한을 재검증한다. 새 키로 같은 estimate를 재사용할 수 있는지, 예산 승인이 단일 실행인지도 명시한다.

근거: OpenAPI `IdempotencyKey`; SQL `generation_jobs`(459행), `approval_decisions`(633행), `budget_reservations`(665행).

### G. SQL의 tenant 경계 밖 불변조건은 전부 별도 구현이 필요하다 — G0 차단

복합 FK는 같은 tenant만 보장한다. 같은 IP/project, 정사 타입/시간 충돌, snapshot과 shot 일치, grant 대상 범위, polymorphic 승인/의존 ID, JSON/UUID 배열 안 ID, 원장 account/reservation 일치는 다수 서비스 검사에 위임되어 있다. 이는 SQL 주석도 인정한 한계다. 운영 역할/GRANT, 신원 bootstrap, RLS tenant 설정과 connection-pool reset, immutable head advancement도 아직 실행 코드가 없다.

해결: 가능한 same-IP/project 참조는 추가 복합키로 DB에서 강제하고, 나머지는 단일 도메인 서비스와 부정 시험으로 묶는다. role 분리와 실제 PostgreSQL RLS 시험을 작성한다. 버전 UPDATE 차단 trigger만으로 DELETE/TRUNCATE와 privileged writer까지 차단된 것으로 표시하지 않는다.

근거: SQL 1~10행, 316행, 374행, 459행, 633~724행, 서비스 제약/immutable/RLS 주석; 기술서 4.4/4.11.

### H. 비동기 완료 결과 연결이 느슨하다 — 초기 계약 보완

`JobAccepted`와 `Job`은 진행 상태는 주지만 typed 결과 참조가 없다. 업로드 완료 후 asset ID, 생성된 plan/storyboard, data-export 파일을 얻는 일관된 결과 계약이 필요하다. 일부 목록/조회 경로는 존재하지만 `Resource` 봉투이고 job과의 연결/결과 형태가 미정이다.

해결: `result: {kind, resourceIds, artifact...}` 같은 종류별 결과와 성공/부분 성공/취소 후 결과 정책을 고정한다. SSE payload만이 유일한 결과 전달 수단이 되지 않도록 새로고침 후 GET으로 복구 가능하게 한다.

### I. G0 범위와 출시 readiness 축을 새로 정해야 한다 — 범위 관리 차단

`core/planned`는 상세도이지 출시 순서가 아니다. G2의 URL import와 분기 생성이 core인데 G1에 필요한 workspace·조회·자산 상태·권리 변경은 planned다. 전체 목록의 75개 G1 baseline을 첫 개발 스프린트로 삼으면 범위가 과도하다. 동시에 G2라는 라벨로 권리 철회·삭제·복원을 유료 서비스에서 미룰 수도 없다.

해결: 별도 G0 capability 목록, 각 기능의 contract/implementation/fixture/runtime 상태, 제외 목록과 완료 증거를 만든다. G1 결제/구독은 저장 스키마 자체도 미완성이므로 G0에서 비활성화한다.

## 5. 보안·권리·비용의 우선순위

**실제 자산을 받기 전**
- 인증된 membership에서 tenant를 확정한다. 클라이언트 tenant ID, 모델이 만든 ID/URL, 문서 내 명령을 권한으로 사용하지 않는다.
- 서로 다른 tenant뿐 아니라 같은 tenant의 다른 IP·외부 reviewer·철회된 계정으로 검색/파일/썸네일/로그/SSE를 공격하는 시험을 만든다.
- 필요한 미디어만 받는 비공개 검역 저장소, 실제 파일 검사, 크기/픽셀/길이/디코드 한도, 격리된 렌더 워커를 먼저 둔다. URL 수집은 G0에서 끈다.
- 권리 선언과 검증을 구분하고, 음원·가사·인물·로고·참조 자산의 허용 용도/기간/제3자 처리 범위를 기록한다. 테이크 승인으로 정사나 사용권이 생기지 않는다.

**외부 유료 생성 전**
- 공급자의 현행 모델 능력·가격·최소 과금·입력 과금·보관/학습 조건을 검증한다. 패키지의 2026-10-23 가격과 지원 표는 활성화 허가가 아니다.
- 사용자 승인 견적에 정확한 모델/데이터/대상 샷/상한을 묶는다. 후보 3개는 성공 보장이 아닌 중지 한도다.
- reserve/job/outbox 원자성, lease fencing, 중복 제출 방지, 제출 불명 대사, cancel/complete 경합, 중복/위조 webhook을 fake provider로 시험한다. 의심 상태에서 새 생성하지 않는다.
- 공급자 원가 USD, 고객 KRW, 크레딧을 분리한다. 결제/구독 자동화는 G0에 포함하지 않는다. 비용 계산기를 원장으로 사용하지 않는다.

**유료 파일럿 전**
- 철회 즉시 새 검색/URL 발급/생성 차단, 파생물 삭제 추적, 원본/선택 take/JSON export, 격리 복원과 tombstone 재적용을 실제 시험한다.
- 기본 5분 presigned URL과 1분 접근 차단 목표의 관계를 결정한다. 엄격한 즉시 철회 대상에는 매 요청 권한 검사 경로가 필요하다는 원문 방침을 구현한다.
- 실제 공급자 출력 품질은 fake provider 시험과 별도로 사람 평가한다. 음원 해시 보존, 프레임/샘플 정렬, 실패·반려·지원 노동까지 기록한다.

## 6. 실행 가능한 G0 구현 순서

G0는 15~30초 내부 기술 실증이며 유료 서비스 준비 완료라는 뜻이 아니다. 기본 UI는 IP·자산/권리, 설정 승인, 프로젝트/샷, 실행/비용, 검토/출력의 5개 작업 영역으로 충분하다. 38개 화면을 먼저 전부 만드는 방식은 피한다.

**G0 제외:** 자동 결제/구독, 공개 공유 링크, 외부 공개/예약 게시, URL import, 다중 공급자 자동 failover, 고급 세계관 분기 UI, SSO/API key 발급, 외주 배정, 다인 군무/긴 립싱크, 3분 전체 MV 품질 약속. 서버 안전 장치를 제외한다는 뜻은 아니다.

기간·예산은 기존 Loretune 코드와 담당 인력 확인 전 확정하지 않는다. 먼저 단계 0~3의 실제 완료 속도와 병목을 얻고 후속 일정으로 환산한다.

## 7. 바로 만들 개발 산출물

1. `G0_SCOPE.md`: 지원/제외, 사용 자산·기간·출력 규격, 완료 증거.
2. `G0_CONTRACT_DECISIONS.md`: 위 A~H 결정과 변경 이유, 원래 FR/TCT 연결.
3. `g0.openapi.yaml` 및 권리/샷/EDL/snapshot JSON Schema.
4. 실제 fixture: 권리 정리된 가상 IP, 짧은 음원/이미지/클립, 2개 tenant·IP, 철회 자산, 손상 파일, fake provider 실패 사건.
5. 버전별 DB migration, 도메인 서비스, 최소 렌더 worker와 회귀 시험.
6. 제품 상태판: `specified → implemented → fixture-tested → runtime-verified → pilot-measured`를 별도 축으로 유지. 문서 수나 endpoint 수를 완료율로 쓰지 않는다.

이 감사는 위 작업을 **제안·준비**한 것이며, Loretune 제품 코드 구현이나 사용자 환경 반영이 완료되었다고 주장하지 않는다.
