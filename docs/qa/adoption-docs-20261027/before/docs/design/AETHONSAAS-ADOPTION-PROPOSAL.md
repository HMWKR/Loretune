## 4. 항목별 도입안: 근거 → 차이 → 변형 → 수용

### AD01. 공통 기준·이번 대상·변경 의도를 한 적용 요약으로 연결

**근거:** S02 D04–05, S03 WR02/04/15, S04 §2–5·§8–10. 프로젝트 공통 스타일/세계 규칙, 이번 인물·제품·장소, 이번 행동을 구별한다. 선택은 이름 문자열이 아니라 정확한 대상·개정·역할을 가리키며, 화면 요약·실제 제출·검토 기대가 같은 해석을 사용한다.

**현재 차이와 영향:** 기존 참조/온톨로지는 보존할 기반이다. 다만 `references.py`의 한 역할당 원본 한 개라는 구조만으로 ‘새 인물은 기존 얼굴 제외, 조연만 기존 캐릭터 유지’ 같은 선택 의미까지 지원한다고 볼 수 없다. 이 경계가 불명확하면 승인된 공통 스타일을 사용하면서도 원하지 않은 얼굴·자료가 섞일 수 있다. 현재 사용자 데이터에서 그 오류를 재현한 보고는 아니다.

**선택·변형:** 기존 서버 해석 경로를 확장해 `공통 기준`, `이번 대상`, `사용하지 않을 자료`, `모델이 지원하지 않는 입력`을 짧게 표시한다. 대상/개정/역할/출처/필수 여부를 실행 snapshot과 연결한다. 내부 `inherit/none/explicit`은 UI에서 ‘장면 기준 사용 / 기존 대상 사용 안 함 / 직접 선택’처럼 설명한다. 현재 모델이 받지 못하는 끝 프레임·복수 얼굴 등을 지원한다고 꾸미지 않는다. 먼저 기존 참조 선택기로 검증하고, rich-text @편집기는 필수로 도입하지 않는다.

**대안:** 모든 설정을 프롬프트에 복사하면 역할·제외·개정의 의미가 사라진다. 반대로 범용 EntityRevision/그래프 DB부터 전면 구축하면 기존 원본·migration 부담이 커진다. 현재 source+snapshot에 필요한 의미만 보강하는 안을 택한다.

**수용 AD01-A:** 같은 자료의 스타일/인물 역할을 구별; 새 인물 제외 시 기존 identity가 제출·검토 기대에 다시 들어오지 않음; 필수 미지원 입력은 전송 전 차단; 선택 입력 제외는 이유와 변경을 표시; 새 개정은 기존 진행 작업을 바꾸지 않음; UI→고정 입력→fake adapter payload를 같은 ID/역할로 대조. 실제 공급자 수용·시각 일관성은 별도 승인된 live 시험 전까지 미검증이다.

### AD02. 대화 초안과 팀 공통 지식의 승격 경계

**근거:** S02 D03/D08, S03 WR05/06/14, S05 WJ04·WCR027. 대화/댓글은 작업 자료이며 자동 상위 지시·공통 설정이 아니다. 이번 요청에 사용하기와 팀 공통 기준으로 채택하기가 다르다.

**현재 차이와 영향:** 같은 작품의 승인 기준을 공유하는 것과 모든 원문/미승인 제안을 모든 대화에 주입하는 것은 다르다. 세션 추가 시 소속만 붙이고 작품 전체 `production_context`를 그대로 전달하면 분리 목적이 약해질 수 있다. 실제 팀원 비공개는 세션 ID만으로 구현되지 않는다.

**선택·변형:** primary의 기존 [세션 계획](CHAT-SESSION-PLAN.md)에 이 계약을 정합화한다. 10/27 계획 상단의 사용자 결정은 복수 대화 생성/전환, 승인 자산 공유, 대화·초안·미승인 제안 격리, 작품 전체 AI 단일 실행 제한 미도입이다. 이 결정들을 다시 미정으로 질문하지 않는다. 새 세션별 DB·별도 chat 엔진을 만들지 않고 기존 부분 구현을 먼저 검토한다. 미승인 제안을 타 대화에서 명시 참조하는 기능은 자동 공유와 다르며 **추가 도입 후보**로만 둔다. 공통 설정 반영은 기존 사람 검토 경로를 유지한다.

**대안:** 모든 대화 자동 공유는 기억 편의가 있지만 정보 혼입 위험이 크다. 프로젝트 자체를 대화마다 복제하면 승인·원장·작업이 분열된다. 공유 canonical + 분리된 대화 초안/제안을 택한 사용자 결정과 맞춘다. 작품 전체 단일 실행 제한을 다시 추천하지 않으며, 병행 실행에서도 공통 예산·예약·멱등성과 공유 대상 충돌을 유지하는 수용시험이 필요하다.

**수용 AD02-A:** 같은 작품 A/B 대화의 원문·초안·미승인 상세가 무단 전달되지 않음; 공유 승인 기준은 같은 revision으로 조회; 명시 참조는 당시 버전에 고정; 늦은 응답이 다른 대화 입력/포커스를 덮지 않음; 기존 CC01/CC02·unknown·예약 한도·기존 turn hash 보존. 다른 사용자 privacy 시험은 AD03의 인증 전제 이후 수행한다.

### AD03. 팀 공개·재사용·채택·승인을 서로 다른 행동으로 만들기

**근거:** S03 WR10–14 및 역할 표, S04 §7, S05 WCR001–004/012–015. 미디어 보기, 입력 정보 보기, 생성에 사용하기는 다른 권한이다. Client는 허용된 후보를 보고 의견을 남겨도 생성·채택 권한이 자동으로 생기지 않는다.

**현재 차이와 영향:** 로컬 `local-owner`와 자산함은 팀 인증/테넌트 경계가 아니다. Take에 권리 설명이 있다고 팀원에게 모든 원본 프롬프트·참조를 공개해도 된다는 뜻은 아니다. 공유 UI만 추가하면 보이는 범위와 실제 파일 접근이 어긋날 위험이 있다.

**선택·변형:** 이 기능은 인증된 actor/workspace/project, 역할별 서버 권한, bytes 접근 정책을 선행 계약으로 둔다. ‘팀 후보로 공유’는 exact Take/version과 명시된 입력 범위를 공개하며, 비공개 메모·다른 버전·공급자 비밀은 제외한다. ‘채택’은 편집 선택이고, 기존 Take 검토·타임라인 승인·최종 납품과 분리한다. 기존 승인 완료 화면에 억지 추가 CTA를 요구하지 않는다.

**대안:** 팀원 모두에게 모든 초안을 공개하는 단순안은 사용자 요구의 미승인 격리와 맞지 않는다. 미디어만 공유하고 입력은 전부 금지하는 안은 안전한 시작점이지만 AD04 가치가 제한된다. **기본 비공개, 결과 공유와 입력 재사용을 별도 허용**하는 단계형을 추천한다. 역할명·초대·보존 정책은 후속 제품 결정이며 aethonSaaS의 Owner/Editor/Client를 그대로 복제하지 않는다.

**수용 AD03-A:** 두 개의 실제로 구분된 테스트 actor와 별도 프로젝트로 목록/검색 수/썸네일/bytes/참조 입력까지 권한 검사; 보기만 가능한 사용자는 유료 생성·채택 불가; 공유 철회 후 신규 접근/전송 차단; 별도 정당한 grant는 보존; 채팅 수신만으로 비공개 자료가 열리지 않음. 이미 내려받은 bytes를 원격 회수했다고 표시하지 않는다. UI role mock만으로 통과시킬 수 없다.

### AD04. 원본에서 허용된 입력으로 새 대안을 시작하는 ‘이어서 만들기’

**근거:** S02 D08, S05 WJ02/03·WCR005–011. 배정·수락이 필요한 인계와 자발적인 새 대안 제작을 구별하고, B가 A의 실행·비용 주체가 되지 않게 한다.

**현재 차이와 영향:** 현재 `reuse_take`는 정확한 파일과 계보를 새 Take로 연결한다. 이는 유용하지만 원래 프롬프트·참조·모델 설정을 안전하게 재구성하는 전체 초안 인계와 같지 않다. 사용자가 입력을 다시 맞추는 수고를 줄일 여지가 있다. 실제 시간 절감은 미측정이다.

**선택·변형:** 선택된 결과에서 새 초안을 만들며 `이어 쓸 자료`, `이번 변경`, `확인할 차이`를 보여준다. 현재 접근·재사용 가능한 당시 입력만 가져온다. 누락된 입력을 최신 값으로 조용히 보충하지 않는다. 원 모델이 이용 불가하면 이유를 보여 주고 사용자가 선택한다. 새 실행은 현재 사용자의 권한·예산·새 견적을 사용하며 기존 job/승인/원본을 변경하지 않는다. 영상 원본에서 첫 프레임을 쓰려면 실제 추출된 이미지 버전이 필요하다.

**대안:** 원 요청 전체 복사 또는 A의 실행 재개는 개인정보·비용·멱등 관계를 손상시킬 수 있다. 파일 배치 복사만으로 입력을 계승했다고 표시하는 것도 부정확하다. 허용 입력 묶음에서 **새 초안**을 만드는 안을 추천한다.

**수용 AD04-A:** 원본/기존 선택/승인 hash 불변; 새 작업의 source Take·입력 revision·변경 의도·실행자 연결; 누락/철회 입력에 선택·대체 경로 제공; 반복 클릭은 같은 준비 요청으로 복귀; 명시 다른 대안은 새 의도; 비교는 실제 접근 가능한 두 버전이며 audition이 채택·승인이 되지 않음. AD03 전에는 단일 로컬 사용자 범위의 인계 준비 시험만 가능하다.

### AD05. 검토 의견 → 확인된 변경안 → 새 버전의 연결

**근거:** S02 D09–10, S05 WJ03/04·WCR016–020. 댓글 위치는 exact version에 연결하고, 사람이 고른 의견만 새 요청의 근거로 사용한다.

**현재 차이와 영향:** 타임라인 댓글, 모션/타임라인 제안, Take 비교는 이미 있다. 댓글 문장을 다시 붙여 넣을 때 원 버전·시점·선택한 의견의 수정 이력이 떨어질 수 있으므로 **기존 기능 사이의 연결**이 후보이다. 모든 댓글을 자동 AI 수정 명령으로 만드는 기능은 제안하지 않는다.

**선택·변형:** 해당 의견의 ‘변경안에 사용’에서 원본 대상·타임코드·댓글 개정을 고정하고, 사용자가 바꿀 내용을 확인한다. AI는 변경안을 제시하고 서버 diff와 기존 사람 apply/실행 승인으로 이어진다. 편집본 길이가 바뀌어도 옛 댓글을 새 영상 같은 초에 자동 이식하지 않는다. 댓글 해결·좋아요·AI 추천은 검토 승인과 다르다.

**대안:** 댓글 전체 자동 실행은 비용·의도 오류를 확대한다. 완전히 분리하면 버전 재설명이 반복된다. 선택한 의견만 명시 참조하는 작은 연결을 추천한다.

**수용 AD05-A:** v1의 의견을 v2 작업에 사용하면 원 대상과 새 대상이 모두 보임; 이후 원 댓글 수정이 고정된 입력을 바꾸지 않음; 다른 자료/유료 모델/범위 변경 시 기존 승인으로 실행 불가; AI 제안만으로 canonical/timeline 변경 없음; 취소·저장 오류·unknown에서 입력 보존; 재생/비교로 실제 결과를 검토할 수 있음.

### AD06. 실제 입력·실행·결과·돈 상태를 한 화면에서 구별

**근거:** S03 WR15–16, S04 §8/11, S06 §4–6·OR004/007/022/024. 요청한 입력, 서버가 해석한 입력, 실제 adapter 제출은 서로 다른 증거다. 결과 생성 성공·자동 검토 완료·사람 승인·비용 정산도 같지 않다.

**현재 차이와 영향:** 이미 모델 snapshot, server receipt, job/reconciliation, 비용·권리 guard가 있다. aethonSaaS 계약을 이용해 **입구별 누락/표시 정합성**을 검토하는 것이 목적이며 새 원장·승인 객체를 병렬로 만들지 않는다. 기존 receipt의 정확한 승인 사실과 모델 설명 분리를 보존한다.

**선택·변형:** AD01 요약과 실제 요청 기록을 연결한다. 사용자 화면에는 대상·현재 모델·준비/실행/복구·결정 시 비용·승인·권리만 보이고, raw hash/adapter/진단은 펼침에 둔다. 실제 제출 전 ‘전송됨’, 모의 결과에 실제 생성 완료, timeout에 실패/비용0을 표시하지 않는다. 계획 모델과 이미지/영상 모델을 계속 독립 유지한다. 새로운 검토 AI 역할·자동 재생성은 이번 안에서 제외한다.

**수용 AD06-A:** 모델/자료 변경 후 이전 견적·승인을 잘못 재사용하지 않음; unknown은 기존 요청 조회이며 새 유료 POST 0; 결과 보존과 정산 미확정 동시 표시 가능; 원칙적으로 같은 상태 용어를 채팅/장면/작업복구에서 사용; 서버 사실과 모델 원문 충돌 시 서버 상태가 우선. fake payload·실제 제출·파일 decode·품질 판단을 따로 기록한다.

### AD07. 현재 문서 권위와 실제 팀 과업의 증거를 관리

**근거:** S01의 current/supporting/historical·scope 관계, S02 D14–15, S03 WR18–19, S10의 계획/성과 경계, S11의 실행별 분모와 미검증 보존.

**현재 차이와 영향:** Aethon에도 원본07, [38AT 추적](../qa/SPEC-MS-001-ACCEPTANCE-TRACE.md), [누락 등록부](../qa/OMISSION-REGISTER.md), [잔여 작업](../qa/REMAINING-WORK.md), manifest가 있다. 따라서 aethonSaaS의 1,150파일 registry나 문서 도구를 복제할 필요가 없다. 현행 근거와 역사 기록 사이의 한정 대체·소유권만 더 명확히 하면 된다.

**선택·변형:** 기존 entrypoint와 추적표에 도입 ID/원천 절/담당/상태/수용/검증 build를 연결한다. 계약 ID는 `SaaS-WR`, `SaaS-CX`, `MS-FR/AT`, `AD`로 구분한다. source 변화·문서 링크/해시 확인은 실제 영향 범위에 한정한다. 문서 registry가 앱 ontology 정본이나 사용자 데이터 저장소가 되지 않는다.

**과업 검증 제안:** A가 권리 확인된 자료로 후보를 준비하고, B가 허용 입력으로 다른 연출을 만들어 비교·선택하는 한 과업을 정의한다. 내부 두 계정 시험은 권한/연결 검증이고, 실제 제작자 두 사람의 관찰은 별도 사용자 연구다. 입력 재구성 누락, 대상/버전 오인, 회복 성공, 찾기·전환·준비 시간 등을 동일 조건으로 기록한다. 절감률·유료 전환·‘경쟁사보다 우수’·90점은 미리 목표 사실로 만들지 않는다.

**수용 AD07-A:** 각 AD 원조건에 구현/격리시험/브라우저/live/사용자 관찰을 별도 연결; 미실시를 PASS로 합산하지 않음; 기존 역사 증거 보존; 문서 변경과 제품 변경을 구분; 단일 writer와 회귀/복구 조건 기록; 정상 전달 성공 ID가 없으면 로컬 산출물로 명시. 새 registry·도구 설치는 별도 필요가 입증돼야 한다.

## 8. 설계 적용과 검증 범위

S07/S08에서 가져올 시각·상호작용 원칙은 **같은 대상 유지, 필요한 도구만 선택 문맥에 노출, 초안·재생 위치 보존, 내부 구조 대신 사용자 행동 표현**이다. 실제 공급자/모델·결정 시 비용·권리·승인·실패는 감추지 않는다. 일반 화면에 raw ID/DTO/원장 구조를 나열하지 않고 진단에서 확인 가능하게 한다.

새 UI는 현재 1920 작업대의 미리보기·transport·타임라인을 보존하고, 1280에서 필수 행동이 접근 가능한지 회귀한다. 고정 workspace의 page-scroll 억제와 긴 패널 내부 scroll/확대 reflow를 함께 검증한다. 실제 browser zoom과 앱 scale은 별도다. source/template 존재로 keyboard/focus/긴 한글/오류 상태를 PASS 처리하지 않는다.

이번 비교는 **문서·선별 코드 조사**다. donor와 대상의 최신 실제 화면을 같은 조건으로 비교하지 않았으며, 고객 시간 절감·시각 우수성·90점·경쟁사 순위를 평가하지 않았다. 외부 공개 사이트나 공급자 문서의 최신 기능도 새로 조회하지 않았다. 따라서 원천 문서에 들어 있는 경쟁사/공급자 예시는 역사적 설명으로만 남기고, 현행 모델 지원 근거로 채택하지 않았다.

## 15. 사용자에게 확인받을 결정과 현재 종료점

이미 확정된 사실은 다시 묻지 않는다: 피벗 경로, 현재 브랜드명, 독립 대화·승인 자산 공유·미승인 격리·작품 단일 AI 제한 미도입,1920주/1280보조/모바일후순위, noMCP/fal·사람승인·기존데이터보존.

부모가 제안 설명 후 확인할 질문은 다음 세 묶음이다.

1. **도입 순서:** AD01 적용 자료 계약 + 이미 확정된 AD02 세션 경계 + AD06 상태 정합화를 우선 묶음으로, AD03 팀 권한/공유 기반 → AD04 이어 만들기 → AD05 의견 연결을 후속으로 두는 안을 채택할지. 전체스택·범용메신저·요금·자동재생성은 제외한다.
2. **문서 반영:** §11의 피벗 보충문과 D01–D12의 현재/역사 상태 정합화 범위를 확인할지. 원본은 보존하며 제품 완료·90·live검증으로 올리지 않는다.
3. **재개 경계:** 문서 정합화 후 primary가 중단된 세션 diff를 먼저 검토하고, 승인된 단계만 구현·검증하도록 할지. 팀원 권한/공개 정책이 정해지지 않은 상태에서 협업 UI부터 활성화하지 않는다.

이 문서는 그 확인을 위한 준비가 끝난 초안이다. 사용자 응답을 받기 전 기존 문서·partial코드·DB·서버를 수정하지 않는다. 이번 신규 시험/공급자호출/설치/Library 업로드는 없고, 로컬 문서 읽기·등록 정합성 검사와 이 파일 작성만 수행했다. 실제 미완성 세션 기능, live/권한/zoom/스크린리더·사용자 연구·최신90·Library 전달 제한은 그대로 남는다.
