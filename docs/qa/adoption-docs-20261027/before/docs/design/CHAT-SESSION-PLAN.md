## 구현 선택과 대안

1. 기존 project JSON에 대화 metadata(id/title/revision/chat 선택)와 기록 소속 인덱스를 추가한다. SQL 테이블 재작성/실DB 마이그레이션 없음. 이전 기록은 안정적인 기본 대화로 해석하며 원래 turn/handoff/hash/원장은 수정하지 않는다. 읽기는 비변경. 기존 서비스에 투영/병합하는 작은 helper를 사용한다.
2. 승인된 canon/자산/타임라인은 작품 공통. 대화 원문, 요청이력, 미승인 계획/온톨로지/편집/모션 제안, 실행/예약은 대화 소속을 서버가 주입한다. 모델의 소속/승인 주장을 신뢰하지 않는다. 새 후보는 자동 채택하지 않는다. 미승인 자산 후보는 생성 대화에서 검토한다.
3. 원자적 BEGIN IMMEDIATE와 기존 request digest 멱등을 유지한다. 대화 로컬 쓰기는 대화 revision+공유 문맥 fingerprint가 읽은 값과 같을 때만 global revision drift를 허용한다. 다른 대화의 순수 초안/도구 작업은 병행 가능하다. 공통 설정/타임라인/자산 채택·승인은 기존 global revision 및 대상 버전 검사를 유지한다. 무조건 last-write-wins, 작품 단일 AI gate, 별도 agent framework는 제외한다.
4. 채팅 실행 active/unknown gate는 해당 대화만 막는다. 동일 요청 키/승인 one-per-prompt와 누적 예산 상한은 작품/원장 전체에 유지한다. 다른 대화에서 unknown 작업 취소/재전송/예약 반환 불가. 작업은 수신 당시 모델·대화에 고정한다. 응답 중 대화 모델 변경은 거절하고 종료/명시 취소 후 변경한다.
5. 최소 선택기/새 대화와 대화별 채팅 선택만 추가. 프로젝트 미디어 기본값·설정은 공유임을 표시한다. 기존 초안 키는 기본 대화에서만 호환하고 새 대화는 별도 키. 전환은 서버 실행을 취소하지 않는다. 늦은 GET/POST가 다른 대화의 입력·상태를 대체하지 않도록 generation+scope 검사한다.

## 순서·복구·중단 조건

S1: helper/Store 투영·소속·충돌 및 legacy fixture → S2: runtime/history/context/model 인계 → S3: 최소 UI/초안 → S4: 관련·전체 회귀/격리 HTTP·두 탭 브라우저 → 증거와 현재 등록부 갱신. 제품 코드 단일 writer. 원본 source baseline은 BASELINE.json으로 고정한다. 실패하면 해당 transaction 전체 rollback; 과거 기록/예약은 보존한다. 세션 데이터가 생긴 뒤 구버전 writable rollback은 대화 혼합 위험이 있으므로 금지한다. 실제DB 적용 전 지원 SQLite backup·행수/hash 검증과 별도 실행 승인이 필요하다. 이번에는 임시 합성DB만 사용한다.

팀원별 권한은 현재 인증 없는 single-local-workspace로 검증할 수 없다. 대화 분리는 보안 테넌트 경계가 아니며 팀 역할·승인자의 범위는 미결정이다. 팀 권한을 가상으로 구현/통과 선언하지 않는다. 공급자 동시 처리량/청구 및 실제 타모델 연동은 offline fake 검증과 구별한다. 누적 실제 usage $0.0381186 유지, 새 API0.

**모델 인계 묶음:** 대화의 작업 목적, 해당 대화의 순서 있는 요청 증거와 최근 공개 응답, 최신 조회로 확인한 허용된 작품 기준/근거, 관련 승인 사실, 허용된 기존 작업의 상태·안정 ID를 서버가 구성한다. 공급자 private reasoning·미완료 provider call ID를 다른 모델로 복사하지 않는다. 이후 도구 결과는 원래 provider/run에 결합한다. 모델의 답변과 서버 영수증을 계속 별도로 표시한다.

‘금지사항 유지’와 ‘자동 해석으로 완벽한 기억’은 다르다. 이번 확장은 CC01의 요청 증거 범위를 분리하는 것이며 새 제약 추출기나 자동 온톨로지 진화를 포함하지 않는다. 실제 정책·권한 제한은 서버가 강제하고, 자연어 요청의 의미적 준수는 별도 모델 품질 시험이다.

사용자가 대화 중 ‘이 작품 전체에서 금지’처럼 공통 범위를 의도한 경우에도 단순히 세션 내부 지시로 축소하거나 정식 IP 사실로 자동 승격하지 않는다. 기존 설정 제안/사람 검토 경로에서 적용 범위를 명확히 해야 한다. 범위가 미확정인 제작 요청은 확인할 조건으로 남기며, 새 대화라는 이유로 기존 서버 정책·승인 제한을 해제하지 않는다. 자연어의 범위를 자동으로 완벽히 분류하는 기능은 이 최소안에 포함하지 않는다.

| 대안 | 이점 | 한계 / 선택 판단 |
| --- | --- | --- |
| A. 작품당 기본 대화 하나를 명시적 ID로만 정리 | 변화가 작고 기존 이력과 가장 가깝다. 대화 주소화/인계 계약 일부를 보강 가능. | 같은 작품에서 독립 작업을 논의할 수 없음. 사용자가 독립 대화를 원한다면 충분하지 않다. |
| B. 기존 모델 상담 안에 선택기와 ‘새 대화’ 추가 | 작품·편집 화면 복제 없이 독립 이력과 모델 선택을 제공. 기존 Store/승인/작업 재사용 가능. | 새 대화의 공유 범위와 동시 실행 원칙을 먼저 정해야 함. **독립 대화가 필요하다고 확인되면 추천.** |

### B안의 저장·API 후보 — 아직 구현하지 않음

- 기존 프로젝트 JSON 안에 `chat_conversations` 컬렉션을 두고 `id`, `title`, `created_at`, `revision`, `chat_selection`(없으면 기본값 상속), `schema_version`을 기록한다. workspace/project 소유권은 Store의 실제 부모 경계에서 결정한다. ID는 서버가 발급하며 사용자가 보내는 actor/owner를 신뢰하지 않는다.
- 새 `chat_turns.body`에는 `conversation_id`를 추가한다. **현재 SQL 테이블/행 순서/기존 body를 대량 변경하지 않는 방안**이다. 현재처럼 프로젝트 행을 읽되 서버에서 대화별로 필터링한다. 큰 이력의 성능이 측정된 뒤에만 인덱스/정규화 migration을 별도 검토한다. 새 대화가 긴 이력의 무음 잘라내기를 정당화하지 않는다.
- 기존 무소속 turn은 작품별 안정적인 ‘기존 대화’ ID로 해석한다. 같은 workspace/project에서 항상 같고 다른 작품과는 달라야 한다. 기존 `session_request_history` schema 1/handoff는 수정하지 않는다. 미래 인계의 schema 2에는 명시적 `conversation_id`와 선택 버전/요청 원장 digest를 넣는다.
- 이 방안은 기존 `Store.mutate`의 `BEGIN IMMEDIATE`·요청 멱등·전역 revision 검사 및 프로젝트 JSON 저장을 재사용할 수 있다(`app.py` 251–267, 658–660행). 별도의 대화 DB/권한 엔진을 만들지 않는다. 전역 revision 때문에 관련 없는 변경도 충돌할 수 있다는 현재 제약은 유지하며 자동 덮어쓰지 않는다.
- 기존 mutation 경로에 대화 생성·대화 모델 선택을 추가하는 후보를 검토한다. 모델 제출/취소/조회/인계에는 명시적 대화 ID를 전달하고 server lookup으로 소유권을 확인한다. 명세의 예시 URL을 새로 복제할 필요는 없다. 새 UI는 ID를 항상 보내고, 구 클라이언트의 ID 생략은 **기존 대화만** 뜻하게 한다. ‘현재 화면에서 고른 대화’로 추측하지 않는다.
- 새 run과 도구 제안에는 대화 출처를 추가하되 action/grant/job의 기존 ID·hash·승인 범위는 재작성하지 않는다. 모델이 도구 인수로 conversation을 바꾸는 경로를 만들지 않고 run의 서버 문맥에서 유도한다.
- `chat_protocols.handoff`의 작품 전체 로컬 대화 주입도 바꿔야 한다. 과거 `project.conversation`은 기본 대화에 한정한다. 다른 대화에서는 승인된 작품 정보와 허용한 작업 요약을 조회한다. 미승인 계획을 전송할 범위는 Q2 결정에 맞추며, 로컬 ‘직접 계획/취향 제안’ 폼을 실제 모델 대화로 재명명하지 않는다.
- 대화 모델 선택은 기존 resolver의 `conversation=`에 연결한다. 작품 이미지/영상 설정은 그대로다. 선택값 저장 가능과 실제 API 사용 가능은 다르며, 현재 합성 입력/문맥/모델/만료 승인 검사와 비활성 registry를 유지한다. 새 대화가 기존 외부 전송 승인 범위를 자동으로 넓히지 않는다.

### 최소 화면·상태

기존 `modelChatPanel`의 제목 옆에 현재 대화명·선택기·새 대화 버튼을 두는 안이다. 전체 작업대나 타임라인을 복제하지 않는다. 일반 화면에는 대화명, 선택 모델/이용 가능 여부, 진행 상태, 초안 보존, 필요한 비용·승인만 보인다. UUID/hash는 진단 영역에만 둔다.

전환 시 입력은 현재 대화 키에 보관한 뒤 대상 대화를 표시한다. 늦은 응답은 원래 대화에 저장하고 다른 대화 초안·포커스를 건드리지 않는다. 서버 실행 상태는 전환과 무관하게 유지한다. 모델 변경은 §3.2의 기본 원칙에 맞춰 현재 응답 종료 후 다음 요청에 적용하고, 즉시 중단을 제공한다면 기존 취소 경로를 명시적으로 사용한다. 모호한 상태에서 새 실행을 자동으로 만들지 않는다.

1920×1080을 주 기준, 1280×900을 보조로 검증한다. 새 컨트롤 때문에 주 작업영역이 밀리거나 초안/오류가 숨겨지지 않아야 한다. 모바일 심층 개선·새 테마·대형 사이드바는 이번 안의 범위가 아니다.

## 7. 결정이 필요한 질문

기존 요구·안전 계약으로 정해진 모델 교체/승인/비용 원칙은 다시 승인받을 문제가 아니다. 아래는 원문이 결정하지 않은 제품 동작이다.

| 질문 | 최소 추천안 | 다른 안전한 선택 |
| --- | --- | --- |
| Q1. ‘세션 기억’에 같은 작품의 **복수 독립 대화 생성·전환**도 필요한가? | 필요하면 B안. 이전 대화의 원문 요청은 새 대화에 자동 상속하지 않고 작품의 승인 기준은 공유. | 연속성만 필요하면 A안 유지. 특정 대화 복제/분기는 별도 요청 때 설계. |
| Q2. 새 대화가 다른 대화의 **미승인 제안**까지 볼 수 있어야 하는가? | 승인된 기준·자산과 이미 접수된 작품 작업은 공유하되, 타 대화 원문/미승인 상세 제안은 자동 인계하지 않음. 필요 시 사람이 해당 제안을 선택해 참조. | 같은 작품의 모든 제안을 공유하되 출처·미승인 표시와 전송 범위를 명시. 현재 `production_context.read`의 작품 전체 제안/plan 목록도 이 결정에 맞춰 분리 필요. |

대화명 수정·보관/삭제, 팀원별 비공개 대화는 현재 추천안에 포함하지 않는다. 실제 요구가 있으면 권한·보존·취소/작업 연결 의미부터 추가 결정한다. 대화 모델 변경은 현재 대화에 적용하고 작품 기본값 변경은 기존 설정으로 남기는 안이 §4.1에 가장 가깝다. override가 없는 새 대화는 기존 프로젝트 기본값을 해석하고, 접수한 run은 그때 선택한 모델을 고정하는 방향을 제안한다.

## 8. 보존·호환·실패 복구

1. 구현 전에 합성 DB 복제본에서 시작한다. 실제 DB 전환은 별도 실행 단계이며 SQLite 지원 backup으로 일관된 스냅샷을 보존하고 무결성·테이블 행 수·기존 turn body/hash/rowid·job/grant/예약 합계를 비교한다. 이번 계획 작성에서는 DB를 열지 않는다.
2. 기존 프로젝트에는 읽기 시 가상의 기본 대화를 제공하고, 첫 명시적 변경 시 같은 ID의 메타데이터만 원자적으로 저장한다. 읽기·재열기만으로 DB를 쓰거나 provider를 부르지 않는다. 기존 turn/handoff/source hash는 그대로 유지한다.
3. 기존 프로젝트별 브라우저 초안 키는 기본 대화에서만 호환해 읽는다. 새 대화 키는 workspace/project/conversation을 포함한다. 저장 검증 없이 구 키를 삭제하거나 다른 대화로 이동하지 않는다. 저장소 차단 시 메모리 입력을 보존하며 영속 보존을 약속하지 않는다.
4. 접수된 기존 run은 원래 handoff·모델·승인 바인딩으로 마친다. 새 대화 추가나 선택이 과거 snapshot을 다시 hash하거나 승인 의미를 바꾸지 않는다. unknown과 이미 쓴 비용은 유지한다. CC02의 ‘명확한 로컬 미전송’과 실제 ‘전송 결과 미확정’을 계속 구별한다.
5. 새 대화 생성은 기존 request ID/digest와 트랜잭션으로 중복 생성·부분 저장을 막는다. 동일 키·다른 payload는 충돌이다. 실패/unknown이면 원래 요청을 조회하며 새 생성·새 전송을 자동 반복하지 않는다.
6. 배포/적용 실패 시 새 세션 쓰기를 중지하고 데이터는 보존한다. **세션을 모르는 이전 바이너리가 작품의 모든 turn을 섞어 읽을 수 있으므로, DB가 열린다는 이유로 안전한 writable rollback이라 하지 않는다.** 새 대화가 생긴 뒤에는 호환 reader로 진단하거나, 신규 기록을 보존한 상태에서 별도 복구를 결정한다. 백업 덮어쓰기로 새 기록을 버리지 않는다.

## 11. 완료·중단 조건과 인계

- 문서 단계 완료: 원문 명시 요구/추론/미결정을 분리하고 현재 저장 경계·호환 후보·Q1–Q3·수용시험을 반환한다. **이번 산출물은 이 파일 한 개다.**
- 구현 단계 완료 후보: Q1에서 B안이 선택된 경우 두 독립 대화 생성/전환/재열기, 자신의 요청 인계, 대화별 모델 선택, 공통 기준·승인/작업/비용 불변과 CS 시험 결과가 실제 증거로 연결되어야 한다. A안이면 독립 대화 미구현을 계속 명시한다.
- 중단 조건: 기존 이력/승인 hash 변경, 다른 대화·작품의 원문 유입, unknown 재제출/예산 초기화, 새 외부 전송 범위·팀 비공개 정책 미결정, 도구 권한 거절. 독립 로컬 문서/fixture 준비는 가능하나 차단된 실행을 우회하지 않는다.
- 현재 영수증 UI의 독립 검증 통과는 유지한다. 승인 사실의 결정성 개선이지 모델 원문 오류가 없어졌다는 뜻은 아니다.
