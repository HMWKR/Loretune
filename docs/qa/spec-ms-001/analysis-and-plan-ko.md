# SPEC-MS-001 분석 및 구현 순서

원문: 프로젝트 루트의 07_Chat_Directed_Multimodel_Production_Spec.md (811행, 28 MS-FR, 38 MS-AT). 원본 및 동반 PDF/DOCX 해시는 source-manifest.json에 기록했다. 루트 Master_Specification.md는 docs/originals 원본과 SHA256가 같다. 동반 PDF/DOCX는 존재·해시만 확인했으며 MD와 내용 동등성은 아직 검증하지 않았다. 기존 133개 자동 테스트 결과를 baseline-regression.txt로 보존했다.

## 공통점과 차이
- 기존 guided.py는 사용자가 작성한 장면을 그대로 구조화하는 로컬 계획이다. 채팅 모델의 tool orchestration이 아니다.
- ontology.py/project_ontology.py의 승인·버전·범위·출처 저장은 서버 문맥의 기반이다. Anthropic 구조화 추출은 제안자이며 제작 도구 실행 권한을 갖지 않는다.
- generation_queue.py와 ledger.py의 실제 요청/불명 접수/비용 예약/수신 차단은 재사용한다. 새 모델 설정이 진행 job, 원곡, 승인 Take, 과거 manifest를 변경해서는 안 된다.
- 현재 fal 실패는 공급자 완료와 앱 미수집을 분리한다. 기존 CDN 403과 추가 요청의 토큰 발급 403은 다른 단계이며 원인 미확정이다. MS-FR-24의 관련 증거이지 통합 성공이 아니다.
- 세 슬롯·명시 선택 우선순위·서버 정책·등록부와 공통 ToolRequest/Result·영속 chat run/action/grant는 추가 구현이 필요하다.

## 충돌과 경계
- 기존 단일 로컬 사용자와 새 조직/연결 소유권 요구는 범위가 다르다. 로컬 principal을 실제 다중 사용자 인증으로 표시하지 않는다.
- 문서의 Next/FastAPI/Postgres는 기존 Python/SQLite를 전면 교체할 이유가 아니다. §15는 기존 DB와 워커 우선을 명시한다.
- 새 문서의 모델 목록은 현재 통합 상태가 아니다. 계정 접근·기능·실제 파일 수신을 확인하기 전 활성화하지 않는다.
- 3 후보/8 도구 왕복/2 수정 시도는 설정 가능한 제안 기본값이다. 무조건 하드코딩한 공급자 계약으로 삼지 않는다.
- 12개 실제 조합은 향후 승인·예산이 필요한 수용 시험이다. 현재 추가 실호출 권한 없음. Anthropic $0.01 시험도 승인 대기다.

## 순서와 완료 증거
1. 역할별 모델 등록부·설정·정책 우선순위, 낡은 수정 거절, 독립 슬롯/이력/고정 문맥. UI와 저장된 값 일치, 재시작 및 다른 작품 격리 검사.
2. 공통 도구의 엄격한 인수·권한 검증. 모델이 actor/grant/endpoint를 주입할 수 없게 하고 중단된 run의 늦은 호출 거절. fake 계약 테스트는 실제 연결과 분리.
3. 기존 계획/원장/job과 action/grant를 연결. 승인한 입력·모델·가격·의존 자산 변경, 중복 실행, 불명 접수, 선행 실패의 원자적 차단.
4. 안내형/상세 UI에 동일 모델 설정과 실제 상태 제공. 모델 교체 후 과거 작업·음악·설정 문맥 보존. 전담 디자인 세션 CSS는 별도 통합.
5. 공급자별 프로토콜 어댑터의 fake 계약과 오류 복구. 실연결·교차 12조합은 미검증 유지하며 별도 승인 이후 수행.
6. 기존 접근성·미디어 QA와 전체 회귀. 모든 96FR/143API/28MS-FR를 한 완료율로 합치지 않는다.

현재 단계 1 착수이며 문서 분석을 제품 수용 시험 통과로 계산하지 않는다.
