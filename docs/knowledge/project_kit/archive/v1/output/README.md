2026년 10월 23일 · 제안 버전 1.0 · Aethon과 별도 사업

## 목적과 현재 상태

아이돌·VTuber·가상 아티스트의 공식 설정, 승인 자산, 활동기, 곡, 제작 이력과 수정 이유를 다음 작품에 연결하는 플랫폼의 사업·제품·개발·UI/UX·검증 계약이다. 완성형 전체 범위를 기술하되 G0~G3의 증거 기준에 따라 단계적으로 제공하도록 설계했다.

**이번 납품물은 실행할 수 있는 서비스가 아닌 설계·개발 계약과 테스트 시나리오다.** 문서와 계약의 정적 연결 검사는 수행했고 최종 PDF 모든 페이지를 시각 검토했다. 실제 생성 모델 호출, 고객 결제·재사용 실험, API 구현, DB migration·RLS, 부하·복원·삭제 시험은 수행하지 않았다. 모든 성능·사업 목표는 미검증이며 테스트 결과는 `not_run`, 실행 결합은 `not_bound`, 기준 자료는 `planned` 상태다.

사용자가 표현한 ‘REA MCP’는 이 문서에서 **Refero MCP**로 해석했다. 실제 조회 근거와 캡처 확인 수준은 `research/refero_evidence.json`에 남겼다. 공식 제품 설명, Refero에 저장된 관찰, 자사 제안을 구분한다. 경쟁사 성능을 직접 시험하거나 조사에 없는 화면 동작을 확인했다고 주장하지 않는다.

## 핵심 제품 계약

1. 첫 작품 생성과 세 번째 작품의 반복 제작 효과를 따로 검증한다. 핵심 사업 가설은 동일 모델·자료·예산의 대조군보다 총 사람 시간과 재작업을 줄이는 것이다.
2. 공식 설정, 원본·생성 자산, 범위가 있는 취향, 피드백 사건을 분리한다. 생성 결과를 자동으로 공식 사실로 확정하지 않는다.
3. 조직 → IP → 활동기·분기 → 곡·프로젝트 → 샷 → 테이크 → 편집 버전의 관계와 사용 시점의 스냅샷을 보존한다. 실제 인물과 공연 페르소나는 다른 객체다.
4. 온톨로지 그래프 작성은 필수 온보딩이 아니다. 출처가 있는 후보를 검토하고, ‘이번 장면에 적용한 기준’에서 사용·제외 근거를 확인한다.
5. 결과물 승인, 공식 설정 승인, 유료 생성 실행, 예산 변경, 다운로드, 외부 게시 권한을 별도로 검사한다.
6. 생성 전에 견적 버전·권한·지원 기능·권리·최대 예산을 확인한다. 접수 여부가 불명확한 유료 요청을 새 요청으로 무조건 재시도하지 않는다.
7. 한 샷을 수정해도 수정 대상 밖의 승인 테이크·음원·자막·버전이 보존되어야 한다. 변화가 필요한 인접 타이밍은 먼저 알린다.
8. 온톨로지 검색이 정확해도 생성 영상의 얼굴·의상·군무 일치가 보장되지는 않는다. 제작 모드와 인물 수·길이별로 품질을 검증한다.

## ‘몇 번이면 되는가’의 합격 기준

아래는 지원 범위에 대한 제안 목표다. 고객과 실제 생성 결과로 측정하기 전까지 약속으로 쓰지 않는다.

| 단위 | 초기 제안 |
|---|---|
| 최초 온보딩 | 기준팩에서 사람 능동 작업 P50 20분 이하 / P90 40분 이하 |
| 후속 제작 준비 | 사람 능동 작업 P50 5분 이하 / P90 10분 이하 |
| 초안 실행 전 결정 | 주요 결정 P50 4개 이하, UI 동작 8~12개 설계 예산 |
| 샷 생성 후보 | 최초 포함 총 3개에서 자동 중지. 추가 유료 실행은 새 견적 승인 |
| 단편 수정 | 지원되는 단순 30~60초 요청의 80% 이상을 2회 이내 수정으로 완료 |
| 그룹 정체성 | 담당자의 블라인드 ‘우리 IP답다’ 중앙값 4/5 이상 |
| 기억 효과 | 세 번째 요청의 총 사람 시간 중앙 상대 감소 30% 이상, 대조군 대비 선호 점수 65% 이상 |

전체 영상 완성까지 4클릭, 세 번 생성하면 반드시 성공, 3개 작품만으로 통계적 입증이 된다는 뜻은 아니다. 샷별 후보 수·전체 수정 회차·클릭 수·프로젝트 수는 별도 단위다. 자료 준비, 권리 확인, 생성 대기, 첫 온보딩 비용, 고객 지원 시간도 각각 계측한다. 정확한 분모와 실패 포함 규칙은 제1권과 `evaluation_protocol.json`에 있다.

## 개발과 검증을 시작하는 순서

1. 고객 한 팀의 실제 세 가지 제작 요청, 사용할 자료, 승인자, 예산과 허용 모드를 확보한다. Aethon의 고객·실적을 승계하지 않는다.
2. `fixture_registry.json`의 기준 자료와 공급자 모형을 실제로 만들고 권리·정답 라벨·해시·검수자를 기록한다. 현재는 제작 지시서다.
3. 조직·권한·IP·자료 후보 승인 → 곡 → 계획 → 견적·예산 예약 → 한 샷 생성 → 출력 → 다음 프로젝트에 근거 재사용까지 작은 수직 경로를 구현한다.
4. core API의 구체 필드와 provider capability를 확정하고, 실제 DB migration·RLS·비용 원장·중복 요청·상태 미확정 복구 시험을 결합한다. planned API는 해당 기능 개발 시 구체 계약으로 승격한다.
5. FR별 정상·반례와 IT의 복합 실패를 실행하고 증거를 연결한다. G1 필수 지원 경로와 출시를 막는 결함의 기준을 적용한다.
6. 같은 자료·모델·예산을 가진 폴더+가이드 대조군과 구조화 기억 조건을 비교한다. 최소 3개 다른 요청, 최소 2곡을 사용하며 팀 단위로 분석한다.
7. 실제 결제·후속 제작 기회·재사용·직접 지원 시간·실패 과금·환불을 확인한 후 G2와 G3 기능을 확대한다.

G0~G3는 일정 보장이 아니라 증거에 따른 단계다. 계정 삭제·권한 회수·잘못된 취향 중지·기본 버전 충돌 방지·구독 해지·자료 회수·백업 복원은 고급 관리 화면이 G2여도 G1 운영에 필요한 최소 계약부터 구현한다. API와 화면을 먼저 늘리고 이러한 기본 경계를 나중에 붙이지 않는다.

## Refero 조사와 UI/UX 사용법

실제 조사 로그에는 26개 질의, 3개 전체 스타일 조회, 12개 전체 화면 메타데이터, 직접 확인한 화면 이미지 4개, 전체 흐름 5개와 공식 설명 자료가 포함된다. 나머지 메타데이터 화면을 모두 직접 조작·시각 검증한 것으로 해석하지 않는다. 캡처 날짜가 알려지지 않은 화면은 최신 라이브 UI라고 단정하지 않는다.

제4권에는 검색어·대상 역할·화면·관찰 수준·입력·행동·출력·권한·비용·버전·실패·다음 화면·채택/제외 이유를 추출하는 규격이 있다. Linear의 정보 위계, Frame.io의 미디어 검토·비교, 자료 업로드·예산·초대 흐름을 작업 목적에 맞게 사용한다. 특정 제품의 로고·브랜드·랜딩 화면을 그대로 앱 전체에 복제하는 설계가 아니다.

## 증거와 변경 관리

`research/`는 출처·관찰·한계를 담는다. `qa/visual_review_01.json`~`04.json`은 납품 문서의 최종 시각 검토 기록이며, `output/Specification_Validation_Report.json`은 정적 연결 검사 범위를 설명한다. 문서 검사 합격과 제품 기능 시험 합격은 구분된다.

실제 시험을 수행하면 앱 commit, schema 버전, provider·model 버전, prompt·평가 지침 버전, fixture hash, 실행 시각, 결과 파일, 실패 이유와 재시험 기록을 추가한다. 목표를 바꾸면 기존 기준과 결과를 보존하고 새 실험으로 등록한다. `MANIFEST.sha256.json`은 패키지 구성 파일의 무결성 확인용이며 제품 성능 증거가 아니다.
